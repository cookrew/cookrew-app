[P0] Owner takeover displaces bookkeeping after the dispatch has already crossed the irreversible boundary
WHERE: src/main/producer-lease.ts:12-25,85-109; src/main/ask.ts:204-231; src/main/dispatch.ts:1463-1503,1646-1683; src/main/index.ts:849-854
CLAIM: `displaceDispatch` treats a durable ledger interrupt as if it cancelled the backend submission, but it neither aborts the already-running agent turn nor clears a fallback paste that already reached the TUI; owner work is then submitted beside consumer work.
EVIDENCE: In the native leg there is no await between lease acquisition and `promptAgent`, so whenever an owner can observe a dispatch-held lease, `promptAgent` has already been invoked and may already have submitted the consumer prompt. `guardOwnerSubmit` calls `TurnTracker.onOwnerPreempt`, whose production wiring only calls `DispatchService.interruptAgent`; that stamps the ledger interrupted and cancels future leg actions, but sends no interrupt to herdr or the agent. The owner then replaces the dispatch hold and immediately calls its own `promptAgent`, creating the two-live-producer case the lease was meant to prohibit. The fallback has the same shape after its first paste write: cancellation suppresses its CR, but takeover leaves the consumer brief in the shared input box and immediately submits owner bytes; the next submit can carry the cancelled text. A committed accounting transition is not proof that irreversible agent input was undone.
FIX: Never displace a dispatch-held submission window unless the backend provides and confirms an actual input/turn abort plus input-buffer cleanup. The conservative rule is: owner takeover may preempt an armed dispatch before it acquires the lease, but once a dispatch holds the lease, owner submissions refuse/wait until the leg acknowledges and releases. Treat partial-paste cancellation as a contaminated input buffer that must be resolved before any new producer can submit.

[P0] Most PTY producers still bypass the producer lease
WHERE: src/main/ask.ts:307-318; src/main/mobile-server.ts:474-505; src/main/mobile-api.ts:646-680; src/main/routines.ts:94-101; src/main/fork.ts:137-151; src/main/turn-tracker.ts:1567-1585
CLAIM: Only `askTerminal` and dispatch delivery acquire the new lease; raw CLI input, mobile `/input` and `/raw`, canvas keystrokes, routines, and fork injection still write directly through `PtySession.write`, which cannot associate their writes with an owner holder or hold a lease across split paste/Enter sequences.
EVIDENCE: `askRaw` sends a bracketed paste, waits, then sends CR with no lease or `stillValid`. While a dispatch is armed but has not acquired its lease, the guard allows the non-submitting paste; the dispatch can then acquire and submit natively into a TUI whose input box already contains owner text. Conversely a paste refused during a dispatch-held window can be followed by a lone CR after the lease releases, the self-flagged boundary bug. Mobile input, routines, and fork injection have the same two-write shape. The inverse is also open: while typed/native `askTerminal` holds an owner lease, `guardOwnerInput` checks only `holder.kind === 'dispatch'`, so unrelated renderer/mobile PTY bytes pass and can interleave with the owner's submission. A lease consulted by only two producer classes is not the one-producer mutex claimed by A3.
FIX: Put every submission-capable producer behind one lease-aware submit primitive. Source-tag owner writes with their holder identity, hold across multi-write input, and return an explicit refusal instead of silently dropping individual bytes. Raw/control input that cannot be classified must refuse while either producer kind owns the window; do not infer atomicity from per-write guard calls.

[P1] Terminal retirement cannot clear a stranded producer lease
WHERE: src/main/producer-lease.ts:74-132; src/main/index.ts:1152-1166; src/main/herdr-agent-wait.ts:98-117,147-150
CLAIM: ProducerLease has only holder-checked release and no terminal-retirement operation, so remove, CWD rebind, backend death, or app teardown can leave an old asynchronous submission holding the same terminal id until its promise eventually resolves.
EVIDENCE: `retireTerminal` interrupts dispatch bookkeeping, clears turn facts, unwatches, and untracks, but never clears the process-wide lease. Native `promptAgent` is an `execFile` wait that can last up to the ask timeout; a kill or rebind does not synchronously settle that promise. A reborn session uses the same node id, so its dispatch delivery sees `held-by-owner` and fails, and its owner ask sees `held-by-owner` and refuses, even though the holder belongs to the dead session. The lease deliberately has no expiry, generation, or force-retire seam, so only the stale caller's eventual `finally` can recover it.
FIX: Generation-scope holds to a concrete terminal/session lifetime and add `retire(terminalId, generation)` that invalidates that generation during every permanent teardown/backend-death path. Late releases must remain generation-checked no-ops. Abort the associated async CLI child where possible.

[P1] The async admission refresh can latch stale forever or fork once per failed request
WHERE: src/main/herdr-host-multiplexer.ts:430-448,469-518
CLAIM: The refresh no longer blocks Electron main, but the hard-coded `execFile` has no timeout/backoff and failure leaves the cache timestamp stale, so a hung child permanently latches single-flight and fast failures spawn a new CLI on every later admission.
EVIDENCE: `admissionRefreshing` resets only in the exec callback; an unresponsive `herdr pane list` has no Node timeout and prevents all future publication. On an error callback the old `admissionCache.at` is not advanced, so the next request immediately launches another child. This recreates process amplification during the exact herdr outage the cache is supposed to degrade through. A cold call also invokes synchronous `available()` before starting async work, and the hard-coded exec bypasses the injected runner, which is why no structural test covers the new refresh path.
FIX: Inject an asynchronous runner, apply a bounded timeout, publish a failure/backoff timestamp, and kill timed-out children. Prime/probe outside admission so `sessionExistsCached` and every refresh path contain zero synchronous runner calls. Test hung, fast-failing, and recovery cases with spawn counts.

[P1] Atomic tail safety regresses the per-turn path to O(total history)
WHERE: src/main/session-sync.ts:579-613; src/main/turn-store.ts:449-517; scratchpad/v5-export-concurrency.html:97-99,224-233
CLAIM: `rewriteTail` is crash-safer than truncate-plus-append, but it now reads, concatenates, writes, and fsyncs the entire uncapped ledger for each tail delta, directly violating A6/I3 and the round-6 O(delta) fix.
EVIDENCE: SessionTurnSync polls every two seconds and emits a tail whenever the open parser record grows or finalizes. `rewriteTail` calls `readFileSync(file)`, builds `Buffer.concat([prefix,replacement])`, and atomically writes the whole result. A long active turn can therefore copy a 91 MB history repeatedly as assistant/tool records append, making cost proportional to total history and potentially O(N squared) over the session. The commit documents a 1.4 MB observed ledger as "bounded", but histories are explicitly uncapped and the design's structural invariant is independent of today's sample size.
FIX: Use an append-only versioned tail record, small tail-overlay/segment, or another atomic format whose durable write is O(changed bytes); compact outside the hot reconcile path under an explicit bounded policy. Extend the delta gate to count bytes read and written for repeated tail updates against a large pre-existing ledger.

[P1] Snapshot-plus-log compaction is not crash-consistent for full annotation saves
WHERE: src/main/turn-annotations.ts:242-294,327-375,419-467
CLAIM: A full save writes the new annotation snapshot and then separately unlinks the old op log; a crash between those operations can replay stale log entries over the newer snapshot and lose underivable title/read/scroll state.
EVIDENCE: Suppose the snapshot says title A, the log later sets title B, and a full `save` now writes complete truth title C. `persistSnapshot` atomically renames the C snapshot, then unlinks the B log. If the process dies in that admitted window, the next `readDisk` loads C and replays the surviving log to B. The in-memory `pendingFull` retry cannot survive that crash. The operation is idempotent only for `maybeCompact`, where snapshot state exactly equals replayed log state; it is not idempotent for full rebuild/reset/migration carrying newer values. Empty saves have the symmetric unlink-snapshot-before-unlink-log resurrection window.
FIX: Give snapshot and log an epoch/generation and replay only log entries matching the snapshot generation, or atomically publish a manifest/directory generation that names both files. Crash-test every boundary of full save and empty save, then reopen a fresh AnnotationStore and assert the newest complete state.

[P1] The atomic-file helper can publish a short or not-durably-renamed replacement as success
WHERE: src/main/turn-annotations.ts:151-198; src/main/turn-store.ts:349-356,509-517
CLAIM: `writeFileAtomic` performs one unchecked `writeSync` and treats parent-directory fsync failure as success, so the helper's callers can publish in-memory success after replacing the only ledger/snapshot with incomplete or rename-not-durable bytes.
EVIDENCE: Node's `writeSync` returns the number of bytes written and is not guaranteed to consume the whole buffer; disk pressure can produce a short write. The return value is ignored, the partial temp is fsynced and renamed, and TurnStore then advances its written-tail metadata. Separately, a directory fsync error is logged but not thrown even though the code itself says the rename is not yet durable; AnnotationStore/TurnStore therefore drop retry state and claim success. This reopens the data-loss class the atomic rewrite was introduced to close.
FIX: Loop until every byte is written or fail, preserve mode, and propagate directory-fsync failure so callers retain dirty work. Add injected short-write and directory-fsync-failure tests proving the old file or retry candidate survives.
