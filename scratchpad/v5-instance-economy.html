v5.1 — 双平面并发与工作流实例经济

对 v5 设计的关键补全(owner 裁定):同一 agent 上的并发会污染 owner 的上下文;消费者调用的对象必须是 agent team template 的实例。本文从第一性原理推演其性能与实用性,并建立盈利模型:卖工作流实例,不卖 agent 使用权。 Conductor · 2026-08-16 · 补全 scratchpad/v5-export-concurrency.html 的 A3/S7

1 · 为什么"租用 agent"在物理上就是错的

Agent = 进程 + 上下文,而上下文是 owner 的资产。往一个活着的 agent 注入外部任务,三重事故同时发生:
① 污染 — 外部 turn 永久进入 owner 的对话史(转写是 append-only 的,rail 上抹不掉);
② 泄漏 — 回答是从 owner 的全部上下文生成的,机密沿回复流向消费者;反向,消费者的数据也进入 owner 的档案;
③ 串行 — 一个对话一次只能回答一个问题(这是 LLM 会话的物理属性,v5 的每 agent 单飞行槽只是承认了它)。同一 agent 的"并发"不存在,只有排队。

所以并发的正确来源从来不是"让一个 agent 同时干几件事",而是多开几个 agent。消费者平面上,这个"多开"必须是 模板实例化:干净的上下文、干净的目录、干净的凭据——每一单都从同一个已知起点出发。这正是上一版 workspace template / instance factory 的根本动机;它当年败于 serviceState 旗标泄漏(38× 事故),而不是败于模型本身。

2 · 双平面并发模型

A8 — 并发出自实例化,永不出自共享。owner 平面:dispatch 打到自己的活团队(自己的上下文、自己的风险),每 agent 单飞行槽——这是编排工具。consumer 平面:请求实例化一个 team template,工作发生在实例自己的 agents 上;消费者的凭据 scope 从铸造起就只包含实例的 agents,owner 的 agent 对它不是被拒绝,而是不存在(404,不确认存在性——r1 修复已落)。

v5 新事实对实例经济的意义
派生 tracking:无 dispatch、无订阅者、无焦点的实例观察成本恰好为零可以持有很多实例而 app 不付税。38× 事故的"孤儿 hot 工作区"类在结构上不存在——上一版 factory 的死因被移除,模型可行了
A2:转写文件就是全部持久状态;O(Δbytes) 观察park = 杀进程留文件,resume = --resume 从文件复活。持久化免费获得,停着的实例内存为零

层状态交付延迟驻留成本适用

4 · 盈利模型:卖工作流实例,不卖 agent 使用权

A9 — 商品是结果的信封,不是机器的时钟。消费者买的是"这个 brief 交给这个版本的工作流,产出这类 artifact"。定价对象是 run/驻留,而不是 tokens 转售——tokens 是成本侧,信封是收入侧,差额就是模板 IP 的定价权。

SKU 阶梯

SKU形态价卡(quote.ts 原生支持)成本侧毛利来源
RUN一次性:brief 进 → artifact 出 → 实例回收/销毁base + perTurn,quoteHash 锁定报价单,cap 封顶tokens + 温池摊销模板剧本的成功率/质量溢价
SESSION有界租期:实例专属,park/resume,上下文跨 run 延续base(时段) + perTurn 计量;parked 停表tokens + 驻留内存时段连续性(上下文积累归消费者这单所有)
DEDICATED常驻团队:月费 + 用量;消费者自己的持久工作区月费 + 计量;SLA(温池保活)常驻内存 + tokens可用性承诺 + 深度定制模板

为什么这个模型在经济上成立

结构机制
IP 复利模板(角色+提示词+技能+编排剧本)一次沉淀,边际复制成本≈0;每次 run 的转写是改进模板的养料 → templateVersion 迭代 → 同一 SKU 提价或开新档。卖使用权是卖工时;卖实例是卖被验证的剧本
成本对齐三温层让驻留成本是显式旋钮:温池深度 K = f(到达率, 内存价, SLA)。派生 tracking 保证闲置实例零观察税——供给可以远大于并发需求而不烧钱
结算可信r1 修完的机器就是收银台:完成=转写终局性+prompt 身份(不多收);replay+tombstone(不重复收);interrupted≠failed(平台故障不按 agent 失败收);quoteHash(报价即合同);fail-closed 账本(收了必有据)。x402 receipts(S5)直接落在这些语义上
护城河可保证的隔离与可复现性——"租 owner 的 agent"模式在物理上给不了(§1 的三重事故),纯 API 转售商给不了工作流剧本,这两样恰好是本产品的正交优势
单笔 RUN 的账(示意):
  收入  = quote(base + perTurn × turns)         ← quoteHash 锁定
  成本  = tokens(实例自己的计量通道) + warm 摊销 + 存储(MB)
  毛利  = 剧本溢价 — 即模板把"会用 agent 的人"的判断力装进了可复制的信封
风险闸: cap(spend-cap) · pending-limit · 幂等 tombstone · interrupted 退让

5 · 存档模型:卖的是地图 + 存档,不只是地图(owner 裁定,2026-08-16)

A10 — 模板 = 地图;黄金上下文 = 存档;实例 = 一局游戏。转写文件就是存档文件(A2 的直接推论): owner 的团队在干净房间里"打通"准备阶段 — 读透代码库、建立约定、沉淀判断 — 这份已经工作过的上下文连同 session 文件一起封存为黄金存档(golden save)。消费者实例化 = 复制存档文件、铸新 session id、--resume 复活 — 每个消费者从存档点继续,而不是从零开荒。
游戏语汇系统对应物商业含义
地图(从 0 构建)team template:角色 · 提示词 · 技能 · 编排剧本基础 IP;可被模仿,单独卖护城河浅
存档黄金上下文:每 agent 一份策划过的 session 文件(+ worktree 快照)真正的护城河 — 数小时/天的真实探索劳动,提示词抄得走,存档抄不走
存档点分档存档随 templateVersion 演进:浅档(刚开荒)→ 深档(领域吃透)天然价格阶梯;深档提价
一局游戏实例:copy-on-write 分支 — 消费者的分支归其所有,黄金存档永不变异SESSION SKU 即"继续我这局";隔离承诺不变
读档时间copy 文件 + resume boot(秒级;上下文从文件回来,A2 免费给的)比温池更便宜的"预热":深上下文不占驻留内存
存档的三条红线。 ① 为售而建:存档里是完整对话内容 — 在 owner 私有环境里长出的上下文永远不可售;可售存档必须在净化房间里、以出售为目的从零构建(与 §3 的回收净化同族,但这里是构建期约束); ② 上下文预算:深存档吃掉实例的 context window — 存档发布前必须 compact 到一个"留足工作空间"的水位(compact 就是存档压缩,recovery 弧已实证其语义:同文件边界记录,573.9K→20.3K); ③ 模型漂移:同一存档在新模型上行为会变 — 存档与 templateVersion 绑定发布,升级需回归(журney gate 是现成的验收器)。
