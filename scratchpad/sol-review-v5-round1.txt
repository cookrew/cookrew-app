[P0] Switched-away human turns can drain while they are still working
WHERE: scratchpad/v5-export-concurrency.html:82-84 (A4); src/main/session-sync.ts:128-134,209-217; src/main/index.ts:1673-1680
CLAIM: The derived tracking model does not contain a fact for an ordinary human-started turn after focus leaves, so thirty seconds of transcript silence is treated as completion even when the agent is in a long silent tool call.
EVIDENCE: Workspace switch calls release() and untracks every outgoing terminal. Only dispatches are pinned. noteDrainQuiet() suspends an unpinned watch after 15 quiet 2-second polls without consulting turn phase or positive herdr working/blocked status. Once suspended, a later transcript append has no poller to notice it. A4's stated union includes dispatch, focus, and subscriber, but not an already-running non-dispatch turn whose focus just lapsed.
FIX: Make any observed in-flight turn a derived tracking fact independent of its producer: pin at reliable turn start and release only on transcript-final evidence (with status allowed only to hold it open), then apply the drain grace. Add a switch-during-silent-tool-call test that appends the final record after more than 30 seconds.

[P0] Dispatch durability is fail-open
WHERE: src/main/dispatch.ts:323-345,526-567,751-773,799-802; scratchpad/v5-export-concurrency.html:69,180-189
CLAIM: A dispatch can be accepted, delivered, and later billed even though its reservation/idempotency transition was never durably recorded.
EVIDENCE: appendDispatchRecord() catches every mkdir/append/chmod error and returns success. write() updates memory regardless. dispatch() then reserves, begins tracking, and delivers. A crash after a failed append loses the idempotency key and lifecycle; a retry can execute the work again, and S5 would have no authoritative row on which to settle a receipt.
FIX: Make persistence return success or throw, append/fsync the accepted reservation before delivery, and fail the request closed with rollback of the tracker stamp/reservation if durability fails. Terminal transition write failures must become a loud recoverable ledger fault, not an invisible state advance.

[P1] The landed observer still reparses the full transcript on every append

EVIDENCE: Every mtime/size change executes readFileSync(watched.file, 'utf8').split('\n') and reparses the entire file. [P1] Node removal and rebind tear down observation without ending the dispatch

CLAIM: Permanent lifecycle paths clear the watch and pin but leave the DispatchService reservation/stamp open.
EVIDENCE: removeNode, workspace removal, cwd move, and team-cut call sessionSync.unwatch(), which explicitly deletes pinned state, then untrack/kill the terminal. [P1] Replay does not actually outrank every refusal
WHERE: scratchpad/v5-export-concurrency.html:180-183,223; src/main/dispatch.ts:482-507
CLAIM: The documented replay ordering is false because agent resolution and prompt validation run before the idempotency lookup.
EVIDENCE: A legitimate retry after its agent was deleted returns 404, and a retry whose body is unavailable/empty returns 400, instead of the promised 200 replay. Only busy and the later reachability/context checks are outranked. This makes network recovery depend on current mutable agent state even though the dispatch identity is already durable.
FIX: Authenticate and derive the consumer first, then look up the consumer-scoped idempotency key before resolving the agent or validating a new request body. [P1] Idempotency expires despite the design's replay-always contract
WHERE: scratchpad/v5-export-concurrency.html:69,223; src/main/dispatch.ts:371-379,777-796
CLAIM: A previously used consumer key can execute and charge again after seven days or sooner under record pressure.
EVIDENCE: prune() deletes closed records and their byKey entries after RECORD_RETENTION_MS and also evicts the oldest closed records whenever the map exceeds 5,000. The design says the same idempotency key replays 200 always. S5 cannot provide exactly-once metered dispatch if its dedupe key disappears independently of receipt/accounting retention.
FIX: Persist a compact consumer+key tombstone/request fingerprint for at least the full billing and dispute lifetime (or define and expose a bounded idempotency TTL in the protocol). Never silently turn a key that has a surviving receipt into fresh work.

[P1] Herdr death is not connected to dispatch interruption
WHERE: scratchpad/v5-export-concurrency.html:226; src/main/herdr-host-multiplexer.ts:365-392; src/main/dispatch.ts:585-631,685-729
CLAIM: The design promises that herdr death interrupts every hosted in-flight dispatch, but the supervisor only restarts and logs; it emits no death signal to DispatchService.
EVIDENCE: A server death can make promptAgent fail or leave a submitted/running dispatch with no status and no future turn. Generic prompt errors are delivery outcomes, not an infrastructure-death classification, and otherwise the record remains open until the ten-minute sweep. That delays capacity release and can classify an outage as failed or merely unconfirmed instead of interrupted, which S5 bills differently.
