ANSWERS:
Q1: Read-only evidence supports "resume writes a successor, not the predecessor," but does not justify weak directory isolation. In the real ~/.claude/projects corpus, predecessor 76b1caa1-5cf3-45e4-8a87-cc1f6ab6af40 remained at mtime 2026-07-27T20:13:13+08:00 while successor d899b48c-a7e7-43cc-8f81-c52efeebffd5 was written 2026-07-30T22:07:23+08:00; the successor head replayed 257 messages stamped with the predecessor sessionId. src/main/claude-rotation.ts:185-201 documents the same live behavior: `--resume` mints a new filename and retains predecessor ids in replayed records. Therefore the golden source must live outside Claude's scanned projects tree, each clone must land under a unique real instance cwd/project slug, and the post-resume successor filename must be discovered and rebound. A publish gate still needs an isolated write probe plus pre/post directory manifests; I did not run Claude because this review was read-only.
Q2: Do not use `cookrew ask`, raw PTY input, or a bearer token in the entry agent. Either scope v1 to single-agent instances, or build a constrained instance-internal orchestration RPC that creates normal child dispatches under a server-injected instance principal, preserving producer leases, prompt identity, idempotency, parentRunId, scope, and receipts. My v1 recommendation is single-agent until that RPC and its accounting semantics are specified; a four-agent boot demo is not yet a four-agent product workflow.
Q3: PRs 1/2 may land inert behind a default-off dev flag for unit/integration work, with the meter field absent, but no factory route, dynamic credential, active catalog entry, or consumer dispatch may become reachable before S5. An empty meter on a live token is a free-work bypass, not a harmless placeholder. D5's S4 -> S5 -> S7 order should remain the release order.
Q4: Use whole-attempt rollback-and-recreate in v1. A step-local retry is allowed only for a bounded, proven-idempotent operation before any process/input/credential visibility, using the same saga revision. Once a pane may have booted or any prompt byte may have crossed, uncertainty means retire/stop/remove/revoke the entire attempt and retry under fresh instance/session/node/token generations after cleanup proof. Client retries need a durable idempotency key so an already-active attempt replays instead of duplicating.
