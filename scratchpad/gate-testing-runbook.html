Door B — the live call gate (fully wired, test this end-to-end)

This is the 401 door that works today. Export is owner IPC only (never on the listener — the grant-surface rule); the caller side is HTTP.

  1. Run the app with slugs on. A slug is only a route when multi-instance is enabled: 
    COOKREW_MULTI_INSTANCE=1 # launch the desktop app with this set
    Note the target workspace's slug (rail/dock chip) and the agent terminal's name.
  2. Make a caller keypair (the "other machine"): 
    node -e "const c=require('crypto');const{publicKey,privateKey}=c.generateKeyPairSync('ed25519');\
require('fs').writeFileSync('caller.jwk.json',JSON.stringify({pub:publicKey.export({format:'jwk'}),priv:privateKey.export({format:'jwk'})}))"
  3. Export + enrol (owner, in the desktop UI). Open the agent's Grant panel (GrantPanel / ExportToggle): paste the caller's public key, compare the six-word fingerprint, enrol it, then tick the agent to export it to that caller. Enrolment grants nothing until you tick the agent — that is by design.
  4. Hit the address with no credential → 401: 
    curl -i -X POST http://<host>:8639/<slug>/agents/<name>/ask -d '{"prompt":"hi"}'
# → HTTP/1.1 401  ·  www-authenticate: Cookrew realm="<realm>", challenge=<c>
  5. Get a fresh nonce (unauthenticated, discloses nothing): 
    curl -s -X POST http://<host>:8639/<slug>/api/call/challenge   # → {"challenge":"<c>"}
  6. Sign the workspace-bound payload with the caller's private key. The bytes are exact: 
    cookrew-call/1\n<workspaceId>\n<sub>\n<challenge>
    (workspaceId = the served workspace's id, sub = the name you enrolled the key under; signature is ed25519, base64url.)
  7. Assert → get a Bearer token: 
    curl -s -X POST http://<host>:8639/<slug>/api/call/assert \
  -d '{"sub":"<sub>","challenge":"<c>","signature":"<base64url-sig>"}'   # → {"ok":true,"token":"<bearer>"}
  8. Call with the token → 200 (the agent answers) or 403: 
    curl -i -X POST http://<host>:8639/<slug>/agents/<name>/ask \
  -H "Authorization: Bearer <bearer>" -d '{"prompt":"what is 2+2?"}'

Force each refusal to prove the gate:

Do thisExpect
token minted for a different workspace403 workspace — re-auth can't fix it, so it's 403 not 401
a valid token, wrong scope403 scope
call an agent nobody exported403/404 — an unexported agent doesn't exist to the internet
junk or missing credential401 — absence and forgery are one answer

Door A — the download gate (401 + the only 402)

This is where 402 lives: a priced preset quotes terms and takes a payment proof.

  1. Run the registry: 
    cd registry && npm run build && node dist/main.js --port 8790
# it ships a DEV facilitator (registry/src/facilitator-dev.ts) so the whole 402 handshake runs with no chain
  2. Publish a preset at each visibility: public (free, 200), identified (needs a passkey, 401), priced (needs payment, 402). Publish is POST /v1/presets (author-signed).
  3. Fetch the manifest and read the code: 
    curl -i http://localhost:8790/v1/presets/<id>/manifest
    PresetHeader sentResult
    publicnone200 — discovery costs no identity
    identifiednone401 · www-authenticate: WebAuthn realm="market", challenge=…
    pricednone402 · body {terms:{amount,asset:"USDC",chain,payTo,nonce,expiry}}
    pricedX-Payment: <proof>200 — the dev facilitator settles it
    identified, boughtAuthorization: Bearer <token>200
  4. Test the two payment error voices with the dev facilitator's magic tx prefixes: a ref that settles REFUSED vs one that settles UNVERIFIABLE (see facilitator-dev.ts) — the sheet must accuse the payment for one and apologise for us on the other.
  5. In the app, the download client (src/main/preset-download.ts) turns each of these into a Gate Sheet step (gateWalk): 401 → identify, 402 → pay, 200 → install. The Gate Sheet component renders that picture.

What is NOT yet testable on the wire (app-verified pending)

The R30 "import an agent as a live SESSION" path — serving a whole template so a caller's first gated call mints a sandboxed session — is wired and unit-green but not yet called from the listener: admission must sit post-auth inside handleCallRoutes (the caller's account id is the verified credential sub). So today you can test the per-agent call gate (Door B) and the download gate (Door A) end-to-end; serving a whole session needs that last mint-after-auth wire. Owner-side you can already serving:serve / serving:stop a template over IPC.
