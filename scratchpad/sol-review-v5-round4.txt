[P0] The local-input preemption hook does not establish one producer
WHERE: src/main/pty.ts:400-404; src/main/turn-tracker.ts:990-1021,1042-1055
CLAIM: Exact prompt bytes are not a sufficient dispatch identity because the claimed producer serialization is neither source-aware nor fail-closed.
EVIDENCE: PtySession writes bytes to the child before emitting the input event that reaches preemptOnOwnerSubmit, so preemption cannot stop a competing submission; it only changes bookkeeping after delivery. The tracker then exempts any owner submission whose bytes equal the dispatch prompt because it guesses that it is the PTY fallback, although no source tag proves that. A real owner can submit the same text after arming and before asynchronous delivery, producing two identical turns. It also treats any matching tracked turn as answeredOnScreen without requiring phase === 'replied', so a different owner prompt submitted while the dispatch turn is still thinking/waiting is allowed to overwrite the live tracker state without preemption. Finally, onOwnerPreempt returns no result: if the interrupted-row append faults, the dispatch stamp stays armed while startTurn still opens the owner turn.
FIX: Put the producer guard before proc.write, tag input with its source/generation, and exempt only the specific dispatch fallback write. Every actual owner submission, identical or not, must durably preempt before delivery is allowed; exempt an existing dispatch turn only when it is settled (`replied`) or has durable finality. Make the preemption result explicit and block/queue input if the terminal transition cannot commit.

[P0] Idempotency aliases byte-distinct work
WHERE: src/main/dispatch.ts:306,349-361,790-829
CLAIM: The service's different-work guard hashes a lossy normalized prompt, so one idempotency key can silently replay a result for different code or instructions.
EVIDENCE: promptFingerprint trims, lowercases, and collapses all whitespace before hashing. [P1] The physical dispatch ledger remains unbounded

EVIDENCE: readDispatchRecords and readDispatchTombstones each read and JSON-parse the entire registry. prune deletes only in-memory entries; it never rewrites or rotates the file. [P1] End-to-end observation is still O(total turns) per append
WHERE: src/shared/session-turns.ts:298-304; src/shared/trace-blocks.ts:876-900; src/main/session-sync.ts:563-603; src/main/turn-tracker.ts:363-405
CLAIM: Incremental byte reads and the Pi block builder do not satisfy I3 because every append still projects, merges, dedupes, and schedules the complete history.
EVIDENCE: Codex/Pi records() calls turnRecordsOf(blocks()), which maps every block. Claude records() copies the entire array.
