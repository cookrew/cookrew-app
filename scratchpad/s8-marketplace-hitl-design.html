1 · 支柱一:双浏览器模型 —— HITL 的第一性原理

1.1 本质:不是两台浏览器,是两个权限域

浏览器 = 凭证容器 + 行使凭证的执行环境。"敏感/非敏感"是表象,真正的分界判据是权限的来源:这份权限是谁的、派生给了谁。

agent 浏览器(agent 域)human 浏览器(human 域)
持有派生权限:scoped token、OAuth access token、会话 cookie、WalletConnect 会话、支付信封(x402 upto 限额)根权限:密码、passkey、钱包私钥、支付工具、身份
行使规则信封内自治——"非敏感直接授权"的形式化:凡最坏后果被已授予能力的 scope 封顶的动作,agent 直接做,不打扰人每一次行使都是一次人类在场的动作:授予、签名、批准、验收
永不持有任何根权限——密码/私钥/卡号在结构上进不来—
物理位置owner 基底(headless / canvas / 实例内)消费者自己的设备(桌面真 Chrome / 手机原生 app)

信封规则(envelope rule):agent 在信封内自治,信封本身只能在 human 域变更。加预算、扩 scope、续授权、开新委托——每一次信封变更是一次 HITL;信封内的每一次行使都不是。由此得到产品定律:打扰次数 = 信封变更次数——体验优化的正解是把信封设计准,不是把弹窗做快。

1.2 缝:两域之间只有一种流向、三种事件

权限只从 human 域流向 agent 域,且流过去的永远是派生物,不是原件。web 早已为这条缝造好协议——OAuth 的 "resource owner 的 user agent" vs "client"、WalletConnect 的 "wallet" vs "dapp":双 agent 假设本来就内建在这些协议里,我们只是把 client 从网站换成 AI。

缝事件发生地流过缝的东西协议先例
委托授予(首次连接/授权)human 域scoped token / 会话(带期限与额度)OAuth consent、WalletConnect pairing
逐笔批准(签名 / 超信封支付 / 结果验收)提案在 agent 域组装,批准在 human 域一个布尔 + 签名产物/收据钱包逐笔签名、3DS 确认
会话修复(登录墙/过期/验证码)灰色地带,见 1.3修复后的 agent 侧会话—

运行时形态:缝事件 = dispatch 的一个暂停态(running → awaiting-human → running)。ask/answer 都是 transcript 事件(A2,不引入第二存储);awaiting-human 期间该 session 不接受其他 dispatch(A8,中断是暂停不是并发,与 LangGraph interrupt()/Command(resume) 同构——深查 II 确认的业界唯一先例)。

1.3 会话修复是唯一的灰色地带,按序消解

登录墙修复意味着人的根凭证可能要穿过 agent 域——双浏览器模型唯一的破口,治理顺序:① 出生即派生:黄金存档携带实例自己的账号,实例从不持有消费者身份,多数登录墙根本不出现;② 委托型修复优先:站点支持 OAuth/SSO/passkey 的走委托授予的缝(passkey 物理绑定在人的设备上,结构上无法被键入 agent 浏览器,强制走对形状);③ 兜底才是接管:交互式远程浏览器(CDP screencast + 输入白名单,COOKREW_INTERACTIVE_BROWSER=1,milestone-1 已落)让人直接驾驶 agent 浏览器完成登录——键入的凭证视为烧断在该会话内:不落盘、不回传、不出现在 transcript。

1.4 传输层:抵达对方域的最短路径(owner 三轮收敛)

方向桌面移动状态
把人送进 human 域
(授予 / 批准 / 402 checkout)		卡片 open in browser → 短时效单次签名链接(绑定 ask-id + keyId),HITL 页完成即自动回调翻转 done;画布 fitView({nodes}) 自动聚焦对应卡片推送通知即 focus,点通知 = 平台强制的那一次手势 = universal link 深链直入钱包/原生 app(companion 真锚点模式:装了 app 直入,没装回落 web)机制已有,新写签名链接页

召唤(人不在看时)桌面系统通知手机推送已有

结论:v1 零新增浏览器扩展。Chromium 插件降级为便利项(badge 计数;Chrome 127+ 聚焦时 action.openPopup() 免通知直弹),不在关键路径。钱包扩展永不进 canvas 内嵌浏览器(Electron 不支持 MV3 action popup,且扩展弹窗是独立窗口、CDP screencast 拍不到);桌面钱包类批准由聚焦卡片渲染 WalletConnect 请求(人类可读摘要 + QR/深链),签名回手机钱包——钥匙住在哪,批准就发生在哪。市场层红利:agent 域在 owner 基底、human 域在消费者设备,双浏览器升格为跨机器的信任边界——消费者的私钥与密码物理上不经过我们的基底,这是能写在商品页上的安全承诺。

2 · 支柱二:预设市场与 401/402/403 阶梯

2.2 401/402/403:把 HTTP 语义用足,不发明新协议

状态码问题后端裁决依据消费者侧体验
401身份keyId+secret 校验失败/缺失(S7 凭证,hash-only 存储)插件/网页引导注册登录;机器买家带凭证重试
402支付无有效权益(entitlement)覆盖此 SKU;body 携带报价(S5 quote 复用)人类:浏览器 checkout(可经插件);agent 买家:x402 式 X-PAYMENT 机器支付,为 agent 买 agent 的经济体铺路
403权限已认证已付费但 scope 不符:SESSION 权益调 RUN 接口、并发额度耗尽、该预设要求 OS 隔离而当前基底未达标、token 被吊销结构化错误说明缺哪个权益,不泄露内部状态

关键设计选择:402 的裁决对象是"权益"而不是"余额"。支付成功 → 写入一条权益(SKU × 预设 × 期限/次数)→ 后续请求 402 检查只查权益表。支付适配器(Stripe / x402 / 手工授信)全部收敛为"写权益"这一个动作,可插拔,核心不感知支付方式——和 S7"支付在 create 之前完成,create 只认幂等键"的定稿一致。

2.3 网络层级:LAN → tailnet → internet 是三级信任跳变

层级现状信任假设S8 动作
LAN已有同屋之人不变
tailnet已有(手机 companion, tailscale serve)自己的设备不变;owner 自己消费自己实例走这里
internetS8 新增陌生人 + 陌生 agent公网 ingress(tailscale funnel 起步,量大后托管 relay)只暴露市场 API 面:目录/401/402/403/create/dispatch/HITL 事件流。herdr、pane、terminal 一概不出网。

3 · 闭环:一次陌生买家的完整旅程

浏览目录(公开,无需认证)
→ 点"运行此预设" → 401 → 注册,发 keyId+secret
→ 重试 → 402 → human 域:浏览器 checkout(或 agent 买家 x402)→ 权益写入
→ 重试 → 403 通过(scope=RUN, 隔离达标)→ 201 实例创建(S7 原样)
→ dispatch 任务 → 需钱包签名 → awaiting-human(逐笔批准)
→ 手机推送 → 点 → 深链入钱包 → 审阅并签名 → done 回流,dispatch 恢复
→ 撞上实例自有账号未覆盖的登录墙 → 会话修复:companion 流式驾驶 agent 浏览器登录
→ dispatch 恢复 → 结果 + 收据(S5)→ 实例销毁(RUN)
→ 买家想续玩 → 升级 SESSION 权益(又是一次 402)→ 自己的存档槽位

每一步都落在已定稿的契约上;S8 新写的只有四样:ingress、权益表、ask/answer 事件流、HITL 签名链接页(外加交互式远程浏览器的硬化,已建)。
