CRITICAL

C1 Unauthenticated destructive restore/undo endpoints on the LAN

src/main/mobile-api.ts:572-599 · bound by src/main/mobile-server.ts:127,132 (0.0.0.0, zero auth — verified)

The diff adds POST /api/agents/:id/restore and /restore/undo — routes that kill the agent's CLI process and rebind its session (restore.ts:106-120) — to a server any LAN device can reach with no credentials. Anyone on the same Wi-Fi can curl the endpoint with any checkpointIndex and repeatedly rewind/kill running agents, or undo legitimate restores. The companion's trust model already accepts this for terminal input, but this diff extends the surface to irreversible session surgery.

Fix — require a pairing token (Authorization: Bearer … shown once in the desktop UI) on all mutating routes, or bind plain HTTP to 127.0.0.1 and gate the LAN listener behind the token. Note: docs/briefs/voice-agent-gateway-brief.md already tracks this posture as item P0-1 — this diff raises its stakes.

C2 access-control-allow-origin: * on every API + SSE response

src/main/mobile-http.ts:12 (JSON) and :46 (SSE) — verified

Combined with C1, any web page open in any browser on the network can cross-origin read full session transcripts (/api/terminal/:id/trace, /output) and POST the new restore/undo endpoints — a malicious ad iframe suffices, no LAN foothold needed. Failure scenario: user browses a hostile page while the companion runs; the page fetches /api/state, enumerates terminal ids, and drives restores.

Fix — drop the wildcard header entirely (the same-origin phone UI doesn't need CORS) or reflect an allowlisted origin only.

HIGH

H1 Busy-agent guard defeated by check-then-await ordering (TOCTOU, data-loss risk)

src/main/restore.ts:72-106 — flagged independently by two clusters; verified

busyReason is checked at :72, then the code awaits checkpointRefs (:75 — a read + parse of a potentially multi-MB session JSONL), does sync fs work, and only then calls killAndWait at :106. During that window the agent can transition idle→thinking (user types, a routine fires) and the kill lands mid-turn — tearing the session JSONL being written, which is precisely the corruption the phaseOf docstring (:29-34) says the guard exists to prevent, and it corrupts the previous session that undo depends on.

Fix — re-evaluate busyReason immediately before killAndWait (refuse if it changed), or hold a per-terminal restore lock for the whole sequence.

H2 No error handling in the restore/undo sequence — failure after kill leaves a dead terminal

src/main/restore.ts:49-173 — verified

No try/catch around checkpointRefs, readFileSync, writeFileSync, mkdirSync, or killAndWait. Worst case: killAndWait succeeds but updateNodeUnsafe returns undefined (node removed from another workspace mid-restore) — the code returns fail(...) at :117 but the pty is already dead and never respawned, silently destroying a running agent with no rollback. Also: the truncated session copy written at :103 is orphaned on any failure path (no unlink).

Fix — wrap the post-write section in try/catch; on any failure after a successful kill, attempt spawnTracked(node) with the original binding before returning the failure; unlink the orphaned dest file.

H3 No serialization between IPC and HTTP restore paths mutating the same terminal

src/main/index.ts:1161-1164 vs src/main/mobile-api.ts:572-599, both delegating to restore.ts:49-173

Two concurrent restores (desktop restore + phone undo, or two HTTP posts) both pass the busy check, both killAndWait, then compute patches from the same pre-read node — the second updateNodeUnsafe overwrites the first's sessionLineage/restoreStack, and spawnTracked runs twice, leaving the agent bound to a session whose lineage/undo stack is corrupt.

Fix — per-terminal async mutex inside createRestoreHandlers (a Map<id, Promise> chain).

H4 Pi spawn integration missing — new module is production-dead code

src/main/pi-bind.ts:138-167 · src/main/index.ts:135-190 · src/main/fork.ts:101 · src/main/teams.ts:304

latestPiSession/piLaunchBinding/piFreshCommand are called only from tests. spawnTracked has branches for claude/codex/opencode but no isPiCommand branch, and piSessionId is only ever assigned null. A user picking the new Pi preset (presets.ts:15) spawns bare pi in the default cwd-encoded session tree, so two Pi terminals in the same cwd share one session tree — the exact cross-agent race pi-bind's header says it exists to eliminate. The pi branches in trace.ts:264 and recover-gate.ts:63-66 are unreachable.

Fix — add a pi branch in spawnTracked calling piLaunchBinding({command, cwd, terminalId}) and persist the returned sessionId; or hold the preset out of this commit.

H5 killAndWait fails silently on timeout

src/main/pty.ts:514-535 · callers restore.ts:106,152

If the tmux session survives the 5s deadline the loop just exits and the promise resolves normally — no throw, no log. Restore then rebinds the node to a new session id and respawns; new-session -A reattaches to the surviving old session and ignores the boot command, leaving the node pointing at a session id no process is running — the phantom-session-id divergence class this codebase has already been burned by. The timeout path is untested.

Fix — throw (or return a status and have restore fail loudly) when the deadline expires; add a unit test with a fake has-session that never dies.

H6 segmentOfFile re-reads and re-parses the entire session file on every size change

src/main/trace.ts:188-198, called from boundaryMarkers up to 3× per invocation

A polling checkpoint rail against an actively-growing session file is O(n²) in I/O and parse time (a 100 MB JSONL fully buffered and reparsed per appended byte-range), contradicting the module's own "I/O is WINDOWED and ASYNC" contract (trace.ts:3).

Fix — route through the incremental blocksOf cache, or memo on a byte-offset and parse only the appended window.
