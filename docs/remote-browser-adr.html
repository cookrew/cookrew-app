How the phone drives the agent's browser

Deciding the frame-source and control model for the interactive remote browser — with human-in-the-loop login as the deciding use case.

Status  Decision — recommend single-instance Flag  COOKREW_INTERACTIVE_BROWSER Date  2026-07-24 Commits  6c08ae8 · 198e73c
◆ Decided & proven — C

One headless Chromium, streamed everywhere. A single --headless=new Chromium child, driven over CDP, with one screencast fanned out to every client (desktop and phone) and input via the closed Input.* vocabulary. One instance means cookies, session, and DOM are unified — the human logs into the exact page the agent keeps. Milestone C-1 proved all six criteria end-to-end (below); the decisive one — a shared sessionStorage token across the agent and two viewers — is the thing OSR structurally could not do.

Context

What we're deciding

A phone can view and drive a desktop browser pane over a WebSocket — JPEG frames down, input up via the Chrome DevTools Protocol. The hard requirement is human-in-the-loop (HITL) login: the agent opens a site, hits a login wall, hands off to the human, then continues on the now-authenticated browser. The question is what produces the frames and which browser instance the human actually logs into.

Three candidates emerged. They share the same control channel (CDP Input.*, a closed input vocabulary — never raw CDP) and differ only in the frame source and, critically, in whether the human and the agent share one page instance or two.

How we got here

The path to this decision

  1. Dispatched: CDP screencast + Input.* over WebSocket

    Built and committed (6c08ae8), secured, benchmarked. Page.startScreencast on the desktop webview + CDP input. Milestone-1 numbers looked excellent: ~5 ms latency, ~100 fps.

  2. Phone test failed: still can't touch

    The bench measured a freshly-mounted, visible node. On a real (offscreen) pane, no frames arrived. Root cause: Chromium throttles compositing of occluded webviews, so startScreencast emits nothing when the desktop isn't showing that pane. The input half was always fine.

  3. Fork: only the frame source needs to change

    capturePage() is the one call proven to force a paint on an occluded webview — that's why the old static thumbnail worked. Three options put forward: keep screencast (dead offscreen), a capturePage loop, or an offscreen-rendered (OSR) window.

  4. Detour: OSR chosen for its fps ceiling

    OSR isn't occlusion-throttled, so it streams continuously. Built with a shared session partition for auth. But an OSR window loads a separate second instance of the page.

  5. Divergence surfaced — and a stray blank window

    A visible "No content under offscreen mode" panel appeared (an offscreen window can't composite to screen), and the HITL-login question exposed the real cost: the human would log into a copy, not the agent's page. This ADR is the result.

The core constraint

Why OSR can't win the login case

Two structural facts, neither fixable in our code:

1 · An offscreen window can never be shown natively

An OSR BrowserWindow has no on-screen surface — its content is only retrievable as a bitmap via the paint event. So the desktop must keep its own separate on-screen <webview> to display anything. OSR therefore forces two instances by construction; the divergence is intrinsic, not incidental. (The "No content under offscreen mode" panel is exactly this fact leaking on screen.)

2 · sessionStorage can be copied, never shared

By the Web Storage spec, sessionStorage is scoped to a single top-level browsing context: it is copied once at context creation, then the two areas are permanently independent. The shared session partition covers cookies, localStorage, IndexedDB, cache, and service workers — but not sessionStorage, and not in-memory JS state. No Electron or Chromium flag changes this.

The unfixable hole So under OSR, "carry the login over" reduces to a one-time copy of sessionStorage plus a desktop reload — which still misses tokens the site keeps only in memory or in mid-SPA state, and the reload destroys the very DOM/route state you were trying to preserve. You'd ship "login carries over, unless…", conditional on where each site happens to store its session.

The deciding use case

HITL login, walked through both ways

OSR (two instances) conditional

  1. Agent opens the site on the desktop pane → login wall.
  2. Human logs in on the OSR copy via the phone.
  3. Auth lands in the OSR copy's context.
  4. Agent continues on the desktop copy — logged out unless the token sat in a shared store and the desktop reloads.
✗ Breaks on sessionStorage / in-memory auth

capturePage (one instance) just works

  1. Agent opens the site on the desktop pane → login wall.
  2. Human drives that exact pane from the phone.
  3. Login completes in place — cookies, all storage, DOM, memory, everything.
  4. Agent continues on the same page — no transfer, no reload, no caveats.
✓ Works for every auth type

Best practice

What the production platforms actually do

Every reviewed agent-browser platform handles live HITL the same way: one shared session with in-place human takeover. None fork a second instance and transfer auth. Cross-instance state transfer exists only as an offline persistence primitive (profiles / storageState) — and even those deliberately exclude sessionStorage.

The reframe

The real issue: remote-displaying a headless browser

Every hard problem here is one problem in disguise: you cannot natively show a browser that isn't composited to a screen, so you are forced to remote-display it. The offscreen throttle killing startScreencast, OSR's "No content under offscreen mode", the frozen passive animation, paintWhenInitiallyHidden — all of it is the friction of streaming an instance that stopped painting to a real screen.

That splits the decision into two coherent single-instance answers. Both solve login; they differ only in what the desktop pane is.

A · Keep it composited fits today

The one instance stays a real on-screen <webview>. Desktop renders it natively; the phone is a remote viewer via capturePage. Never lets the instance go headless, so it sidesteps the display problem entirely. Small addition to Cookrew as it is.

C · One headless instance future / cloud

A single headless browser is the instance; both desktop and phone remote-display it (frames + CDP input) — the Browserbase/Steel model. Uniform, but the desktop loses native browsing and it inherits OSR's paint quirks. Right only if browsers must run with no desktop at all.

The question that decides A vs C Is a desktop always present and primary → A. Or must the browser run headless without a desktop (cloud sessions, server-side agents) → C. For the desktop-first canvas as it stands, A is the fit; C is the migration path if Cookrew goes cloud.

If C — the build path

Headless Chromium, streamed everywhere (not OSR, not WebRTC)

If Cookrew goes single-headless-instance, the researched answer is a real --headless=new Chromium child process driven over CDP, with one Page.startScreencast re-broadcast to every client and the closed input vocabulary translated to CDP Input.* on the same session — the vercel-labs/agent-browser shape, the closest public analog to this exact case.

Why this clears every hurdle A headless window is never composited to a screen, so there is no occluded surface to throttle — startScreencast fires for every frame the page produces, going quiet only when nothing changes. That is the precise failure that sank OSR, and it does not occur headless. The user-data-dir SingletonLock makes agent + all viewers one process on one profile, so cookies / session / DOM are unified for HITL by construction. And it reuses the existing cast code (ws-frame, cast-input, screencast-pace) — only the target changes.

Two things to design around

Slow-client fan-out: CDP gives one stream per session. Re-broadcast the frames to N sockets, but ack CDP immediately and, per client, keep only the latest frame and drop stale ones when a socket is backed up — never apply per-client backpressure upstream to Chrome, or one slow phone stalls the desktop too. (This changes the current single-client ack-on-drain pacing.)

No native UI: CDP screencast can't show file pickers, permission prompts, native <select> popups, or the PDF viewer — the reason Steel moved to WebRTC. Keep login flows DOM-rendered, intercept file choosers via CDP, and hold WebRTC as a documented escape hatch.
