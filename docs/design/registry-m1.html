Registry M1 — the gate, the log, and the seam

P2-A design note · Forge · 2026-08-20 · decision required before implementation
Grounded in docs/design/marketplace-architecture.html §0–7 and the merged M1 client half (feat/marketplace-m1, 00148e7).

The one-sentence shape

The registry is a dumb content-addressed file server behind one authorization function. Every route either serves bytes that are already signed, or asks that function what answer to give. There is no session state, no business logic outside that function, and nothing on the server that a client is required to trust.

1 · Service shape

Recommendation: registry/ at the repo root, standalone Node, no Electron, no framework. Started with node registry/dist/main.js; in dev, run through the repo's esbuild bundle the way the seed script already is.

DecisionChoiceWhy
Locationin-repo registry/ So it imports src/shared/preset-manifest directly. That module is already pure — no fs, no node:crypto, no Electron — and a test enforces it.
Verificationone implementation, two ends canonicalJson and signedPayload are imported, never re-derived. A second implementation of a canonical form is how a signature check quietly becomes decorative: the server would accept what the client rejects, and the difference would surface as "sometimes installs fail".
Transportnode:http Four verbs, five routes. A framework would be more code to audit than the thing it serves.
Storagecontent-addressed files + append-only log Blobs are immutable by construction, so the store is a directory and the index is derived. No database in M1.
Cryptonode:crypto ed25519 Same primitives the publisher already uses.

Layout

registry/
  src/
    server.ts        route table; no logic
    authorize.ts     THE decision function — the only place answers are chosen
    store.ts         blobs/ + manifests/, content-addressed, immutable
    log.ts           append-only transparency log (hash-chained)
    identity.ts      WebAuthn: challenge, verify, short-lived token
    publish.ts       author-key TOFU + countersignature
  data/              runtime: blobs/, manifests/, log.jsonl, identities/
  test/

Deliberately absent in M1

No payments, no entitlement table beyond a boolean, no seats, no revocation, no witness co-signing, no CDN, no rate limiter beyond a trivial per-identity counter. Each is M2/M3 and each has a named seam below. A registry that grows these speculatively is a registry nobody can audit.

2 · The gate endpoint

The whole business logic is which of four answers a request gets, and M1 implements two of them. doc annotation Status codes and reason tokens appear in this note as labels for the design. Per R14 none of them may render in shipped chrome.

RouteAuthAnswersNotes
GET /v1/presets?q=none200 Browse/search. Discovery is deliberately ungated — A2 says the marketplace adds discovery, identity, payment and entitlement, and only the last three are gates.
GET /v1/presets/:id/manifestoptional200 · 401 · 402 (M2) · 403 The gate. Idempotent, so the client's whole recovery strategy is "retry the same request".
HEAD /v1/presets/:id/manifestsame200 · 401 · 403 R3's update check. Answers x-cookrew-preset-version and nothing else.
GET /v1/blobs/:hashnone200 · 404 Content-addressed and immutable, so Cache-Control: immutable is honest. Ungated on purpose: the bytes are useless without the manifest that names them, and the manifest is the gate.
GET /v1/log?from=&preset=none200 The transparency log, replayable by anyone. preset narrows it to one preset's records, keeping their real seq and prev — that is the link R20's rotation sheet hands the buyer, and "verify this yourself" has to land on something a person can read.
POST /v1/presetsrequired201 · 400 · 401 · 403 · 409 · 413 Publish. Fresh WebAuthn ceremony per manifest — and the freshness is real: the first attempt carries no countersignature and is answered 401 with a challenge bound to this operation, author key and preset. 400 is a manifest that does not describe its own bytes, 409 a conflict with what the log already holds, 403 scope a download token at a write route (D4/R26's other direction).
POST /v1/presets/:id/rotaterequired200 · 400 · 401 · 403 · 409 Key rotation (R20's registry half). Same ceremony, different operation — and the difference is inside the countersigned payload, not only in the URL. Both routes exist only when identity does; a deployment that cannot authenticate answers 404 and does not advertise them.
GET /install/:presetIdnone200 · 404 The shared link (R21 Option A). Outside /v1 deliberately: people paste this one into messages, and a version prefix in a human-held URL is a promise to keep it working when the API moves on. Answers HTML, and both answers are a page — somebody following a dead link did nothing wrong and cannot read a status code. Names the preset and stops: name, @handle, version. It is not a review sheet (the manifest is for a client that checked it itself — A5) and it cannot install, because it carries no script, no form and a CSP that forbids both.

F3 — yes: the ungated search carries visibility

Every row from GET /v1/presets carries visibility: "public" | "identified", and that route takes no credential. So the market card renders lock state before any click: a locked chip is drawn locked from the first paint rather than discovered by clicking and being refused.

Worth stating as a rule, because it is a boundary and not a convenience: what a preset costs is public; only what it contains is gated. Hiding the lock until a click would make the first click of every gated preset a failure the user provoked.

Shipped in A1 (PresetSummary) and asserted explicitly in 364d945 — the test fetches search with no credential and checks the locked row.

The 401 path, exactly

  1. Client GETs the manifest with no token.
  2. Server answers 401 with WWW-Authenticate: WebAuthn realm="market", challenge=<b64url>. The challenge is single-use, 90s, and bound to nothing else — it is a nonce, not a session.
  3. Client runs the passkey ceremony and POSTs the assertion to /v1/identity/assert.
  4. Server verifies and returns a token: 10 minutes, scoped to downloads, and worth nothing for publishing.
  5. Client retries the identical GET with Authorization: Bearer.

D4 / R9 — a wrong-scope token is 403, never 401

If a token is valid but does not cover this preset, the answer is 403. Answering 401 would tell a client "your identity is the problem", it would re-authenticate, present the same token, and loop. 401 means prove who you are; 403 means you did, and it is still no. A client may loop on the first and must never loop on the second — that asymmetry is why the codes are the protocol.

F2 — a background check never raises a sheet

The dock-open update check (R3) is not something the user asked for; it happens because they opened a dock. A token lives ten minutes, so meeting an expired one on a HEAD is routine, not exceptional — and its answer is badge state and nothing else: no badge, no error, no sheet.

Every non-200 is silent, not only 401: a refusal, an unreachable registry, a malformed answer. The buyer keeps the version they have, which still works, and learns about a newer one the next time a check succeeds. Raising a passkey prompt because a background poll tripped would mean opening a dock can demand a fingerprint, which is the failure this rule exists to prevent. Sheets are raised by user intent only.

Encoded, not merely written down: updateCheckOutcome in src/shared/preset-manifest.ts returns silent for every non-200, with tests. Shipped 364d945.

What actually needs 401 in M1

M1 has no money, so gating would be theatre — except that an ungated M1 leaves the 401 path untested until M2, when it will be load-bearing. So: a preset carries visibility: "public" | "identified". Public answers 200 to anyone. Identified answers 401 first. Both ship in the dev registry so Magpie's C-area matrix has real traffic to assert against, and M2 changes the reason a request is refused, never the machinery.

3 · Dev-mode passkey on localhost

WebAuthn requires a secure context, and http://localhost is one by specification — so dev needs no TLS and no certificate story. RP ID is localhost, origin is http://localhost:<port>, and both are asserted server-side rather than trusted from the client's clientDataJSON.

WhoAuthenticatorHow
A human on the desktopTouch IDReal ceremony in the market browser card. Nothing special.
Magpie's automationCDP virtual authenticator WebAuthn.addVirtualAuthenticator on their own Chrome. Deterministic, scriptable, and it exercises the same server code a Touch ID prompt does.
Unit testsfixed key pairAssertions signed in-process; no browser.

No bypass switch

There is deliberately no --dev-skip-auth. A flag that turns the gate off is a flag that gets set in the environment that matters, and the 401 path would then be exercised by nobody until a buyer hits it. The virtual authenticator gives automation everything a bypass would, without ever building a door.

4 · Publish auth, and author-key TOFU

This is my review carry-forward, and the part I most want a ruling on.

The client already pins an author key at install (author.pub, H2) and re-verifies every read against it. That protects a buyer who has already installed. It says nothing about the first install, or about version two arriving under a different key.

Publishing

  1. A fresh WebAuthn ceremony per manifest — a download token is explicitly not sufficient (spec §6).
  2. The manifest arrives already signed by the author's local ed25519 key. The registry never sees that key.
  3. The passkey identity countersigns the author key id: the WebAuthn assertion covers sha256(authorKeyId ‖ manifestId). That binding is what the log records.

TOFU continuity

first publish for a preset lineage   → bind (identityId → authorKeyId), log it
later publish, same author key       → accept
later publish, different author key  → REFUSE (409) unless a rotation record,
                                       countersigned by the SAME identity,
                                       is already in the log

Which half is the security boundary

The client's pin is. The registry's TOFU check is a convenience that catches mistakes early and makes the log meaningful — but per A5 a compromised registry can only deny, so a server-side rule can never be what keeps a buyer safe. Stated plainly because it is exactly the kind of check that gets mistaken for protection: if the registry were the boundary, an attacker who owns the registry would own every future version, and the entire signing design exists to make that false.

Open question for the Commander: on rotation, should already-installed clients auto-accept the new key because the log shows a valid countersigned rotation, or refuse and require a human? I lean refuse and surface it — an auto-accepted rotation is indistinguishable from a compromised passkey, and "the author changed keys" is exactly the event a buyer should see once. That costs a sheet Velvet has not written.

5 · Transparency log

Append-only JSONL, one record per publish or rotation, hash-chained so an omission is detectable by anyone who kept an earlier head.

{ "seq": 41,
  "at": 1755993600000,
  "kind": "publish",                       // | "key-rotation"
  "presetId": "sha256:…",                  // content address of team.json
  "version": 3,
  "authorKeyId": "ed25519:…",
  "identityId": "webauthn:…",              // stable per passkey credential
  "countersig": "webauthn:…",              // assertion over sha256(authorKeyId ‖ presetId)
  "prev": "sha256:…",                      // hash of record 40
  "hash": "sha256:…" }                     // sha256(canonicalJson(record minus hash))

Canonicalised with the same canonicalJson the manifests use — one canonical form in the codebase, so a log record hashes identically wherever it is checked.

In M1 the log is written and served. It is not yet witnessed. A single-operator log proves consistency, not honesty: the operator can still fork history for two different readers. Witness co-signing and gossip are M3, and until they land the log's real guarantee is "the registry cannot quietly rewrite what a client already saw" — which is worth having and worth not overstating.

6 · Where M2's 402 mounts

One function, one added variant. Everything else — routes, headers, client retry loop, log — is unchanged.

// authorize.ts — M1
type Verdict =
  | { code: 200 }
  | { code: 401, challenge: string }
  | { code: 403, reason: ForbiddenReason, remedy?: string }

// authorize.ts — M2 adds ONE variant and ONE header read
  | { code: 402, terms: { price, asset, chain, payTo, nonce, expiry } }

The order is fixed and each step answers before the next runs: identity → entitlement → (M2) price → serve. M2 inserts itself between entitlement and serve, reads X-Payment when present, mints an entitlement on verified settlement, and lets the client retry the same idempotent GET (spec §4). No new endpoint, no confirm step, no session — a crash mid-flow retries into either 200 (entitlement minted) or 402 with a fresh nonce (payment never landed).

R5 — the seam is on THIS surface only

402 mounts on the download/chip/top-up path. The call path is a different route with a different answer set — 200 or 403, never 402 — and an exhausted prepaid meter surfaces there as balance_empty between calls. That is already encoded client-side in isCallPathAnswer and DRAWDOWN_CONTRACT; the registry must not be the thing that breaks it. Per R12 the drawdown is per call at accept, which is what makes Velvet's "its last answer completed" true by construction rather than by copy.

7 · How the market card hands INSTALL to the app

R1 puts the market in a canvas browser card, so the page is a web surface and INSTALL has to cross from that page into the app. I found no existing mechanism to reuse — no protocol handler, no navigation interception on browser cards — so this is a real decision, not a detail.

OptionShapeAssessment
A · canonical https deep link Page links to https://<host>/install/<presetId>; the browser card recognises the route and routes it to main. Recommended. One URL that works in three places: intercepted on the canvas, deep-linked into the phone companion, and a real web page for anyone without the app. It is the same shape the phone handoff rule already relies on.
B · custom schemecookrew://install?id=… Needs an OS protocol registration that does not exist yet, is invisible to a browser without the app, and cannot be shared.
C · postMessage bridgePage talks to the card's host. Couples the registry page to Cookrew internals and only works inside the canvas — the phone case dies.

Under A, the app never installs because a page asked. The interception hands main a preset id; main downloads, verifies with the client-side verifyPreset, and shows the review sheet. The page cannot skip the sheet — that is the point of A4, and the seam is designed so a hostile page has no way to express "install without asking".

Dependency to flag: option A needs a small navigation hook on browser cards that does not exist. That is arguably Atlas's surface, not mine. I would rather agree the shape here and file the hook than build a second mechanism inside the registry.

7b · Dev contract — reconciled with Magpie's harness

Magpie published a harness contract and took the C-area 401 matrix live. Reconciled against what 364d945 actually served:

They expectedWas servedNow
/v1/health— Added. Liveness plus a self-description of the contract, so a harness reconciles expectation against reality in one request rather than one 404 at a time.
/v1/dev/identities— Added, dev only. GET lists enrolled credentials, DELETE resets. The reset is the point: a gate matrix must start from a known-empty state or its first case tests whatever the last run left behind.
manifest routeGET|HEAD /v1/presets/:id/manifest Matches. No change needed.
/v1/pay—Will not exist. See below.

/v1/pay is not a gap — it is a design difference, and it matters before fixtures are written

M2 mounts 402 on the manifest gate itself. The client pays, then retries the same idempotent GET carrying X-Payment (spec §4). There is deliberately no confirm endpoint: a crash mid-flow retries into either 200 (entitlement already minted) or a fresh 402 (payment never landed), and never into a state nobody can name.

A separate /v1/pay would reintroduce exactly the two-step stateful checkout the status-code design exists to avoid. Flagged loudly because a fixture built against it would pass its own assertions while testing a route that is never going to exist — so /v1/health names it in a notServed field, with the reason.

The dev routes are absent, not refused, without dev mode, and dev mode is a startup decision rather than a runtime toggle: an endpoint that can forget every credential must not be one flag away in production. Tests assert both the 404 and that /v1/health does not advertise them.

8 · Slice plan, once approved

  1. P2-A1 — store + log + GET manifest/blobs/search, public only. No auth. End state: the seed script's three presets served over http and installable by hand.
  2. P2-A2 — identity: challenge, assertion verify, short-lived token, the 401 path, and D4's 403. Unblocks Magpie's C-area matrix.
  3. P2-A3 — publish: fresh ceremony, countersignature, TOFU enforcement, log records.
  4. P2-A4 — the install handoff, pending §7's ruling.

Each slice ends green with the reviewer's PoCs as tests, on feat/registry-m1 off dev, in a linked worktree. No commits to dev without review.
