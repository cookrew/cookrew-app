SEC-S gate — instantiator slice 1

The acceptance, fixed before the diff exists · Commander · measured against the running install, dev@afb027f

Two structural findings that change slice 1, before a line is written. Both were probed against the live app, not read.

The ruling says Seatbelt wraps ensureSession rather than attachSpawn. In this tree that is backwards for tmux and unimplementable for herdr — and, more seriously, per-session confinement is not reachable at either seam while the tmux server is shared. The same shared server defeats env scrubbing done at spawn time.

Neither is a reason to slow slice 1 down. Both are reasons to point it somewhere it can actually work, now, rather than after a wrapper ships that reviews as correct and confines nothing.

Finding 1 — Seatbelt cannot go where the ruling puts it

Blockstmux's ensureSession is an empty function
// tmux-multiplexer.ts:143
ensureSession(): void {}          // "new-session -A in attachSpawn IS the create-or-reattach"

attachSpawn(spec) {               // ...and this is what actually starts the agent
  return { file: 'tmux', args: ['-L','cookrew', ..., 'new-session','-A','-s',spec.sessionName,
                                'sh','-c', bootScript(spec)] }
}

Wrapping ensureSession on the default backend wraps a no-op. The agent is launched by attachSpawn's boot script — observable in the live process table right now, ending in exec claude --permission-mode bypassPermissions.

For herdr the same wrapper is not merely empty but impossible: its ensureSession creates the pane over a socket, so the process that becomes the agent is a child of the herdr server. A sandbox profile applied inside Cookrew cannot constrain a process another daemon forks.

Blocks…and attachSpawn is not right either, because the server is shared
$ pgrep -fl 'tmux.*cookrew'
63499 tmux -L cookrew -f …/cookrew.tmux.conf new-session -A -s cookrew_6aaaca9d… sh -c …

One server, label cookrew, every pane a child of it. Two consequences:

• Reattach runs no boot script. new-session -A attaches to a surviving session — which is the behaviour this layer exists to protect. Sandboxing the attach therefore sandboxes the tmux client while the agent carries on inside the server, unconfined, exactly as it was.

• A pane cannot be confined separately from its server. The agent's parent predates the session and serves every other session too. sandbox-exec constrains a process and its descendants; there is no seam here that owns only this session's descendants.

So the honest options are two, and both are architectural: a per-session tmux server — its own label and socket, spawned under sandbox-exec, torn down by END — or sessions do not use tmux at all. Slice 1 should pick one explicitly. A Seatbelt call at either existing seam is decorative, and it will pass code review.

Finding 2 — the same server defeats env scrubbing at spawn

BlocksPanes inherit the server's environment, not the spawn call's
$ tmux -L cookrew show-environment -g | grep -iE '^(SSH_AUTH|HOME|KREWCLI|PATH)'
HOME=…
SSH_AUTH_SOCK=…            <-- the owner's agent socket, in the shared server
KREWCLI_KREWHUB_URL=…
KREWCLI_KREW_AUTH_URL=…

pty.ts's own comment already says it: “under tmux/direct the pane (or the tmux SERVER on its first start) inherits this env.” First start. The server here has been up since long before any session; a scrubbed env handed to pty.spawn for session N sets the environment of the tmux client, and the agent in the pane inherits the server's.

An envFor(sessionId) that is perfectly written, unit-tested, and applied at the spawn site therefore passes every test and leaks every key — which is why the ruling's word for this gate is “probe it, do not read the comment”, and why the probe must read the environment inside the agent's pane.

SSH_AUTH_SOCK is the one to look at first: it is not a secret that can be rotated, it is a live handle to the owner's loaded keys.

The gate — four probes, and what each must show

P1Env scrub — read the pane, not the call
tmux -L <session-label> show-environment -g          # server global
cookrew ask <session Conductor> "print env | sort"   # what the AGENT actually holds

MUST be absent: ANTHROPIC_*, OPENAI_*, GITHUB_*, AWS_*, SSH_AUTH_SOCK,
                KREWCLI_*, and any path under the owner's HOME
MUST be present: only the allowlist slice 1 declares

Fails if the assertion is made against the object passed to spawn. The env is scrubbed when the agent cannot see the keys, not when the call site cannot.

P2Turn-store partition — the session cannot write the owner's ledger
before=$(shasum ~/.cookrew/turns/<OWNER_TERMINAL>.jsonl)
# drive a session turn, then:
after=$(shasum ~/.cookrew/turns/<OWNER_TERMINAL>.jsonl)   # MUST be unchanged

ls ~/.cookrew/turns/                 # MUST NOT contain the session's terminal id flat
# the session's ledger MUST live under its own partition, and
TurnStore.loadAll()                  # MUST NOT return the session's records to owner surfaces

Read as well as write: loadAll() is what the board and checkpoint search run on, so a partition that only fixes the write path leaves caller-reads-caller open.

P3Seatbelt — confines the agent, and the symlink is closed
ps -o ppid= -p <agent pid>           # parent MUST NOT be the shared cookrew tmux server
cookrew ask <Conductor> "cat ~/.ssh/id_ed25519"        # MUST be denied
cookrew ask <Conductor> "cat /etc/passwd"              # MUST be denied
ln -s / $SANDBOX/esc && cat $SANDBOX/esc/etc/passwd    # MUST be denied  (/tmp-symlink family)
cookrew ask <Conductor> "cd / && ls"                   # allowed to cd, MUST NOT read

The parent check is the one that catches a decorative wrapper: if the agent's parent is still the shared server, no profile was applied to it whatever the diff says.

P4cwd confinement — enforced, and not bypassable
confine('../../etc', s)              -> null
confine('/etc', s)                   -> null
confine(symlink-out-of-sandbox, s)   -> null      # realpath BOTH sides, then compare
confine(nonexistent, s)              -> null      # refuse, never resolve optimistically

ipcRenderer.invoke('terminal:setCwd', <session terminal>, '/etc')   -> MUST refuse
ipcRenderer.invoke('workspace:dir:add', <session ws>, '/etc')       -> MUST refuse

The last two are the gate that the audit's §4 predicts will be missed: confine at mint is not confinement if moveTerminalCwd still enrols an arbitrary directory afterwards. A startsWith on an unresolved path fails the symlink case — do not copy PresetStore.dirFor, fix it.

Two more I will check that were not in the brief

P5/P6Reachability and permissions

P5 — the IPC surface. Per the audit addendum, pty:attach resolves out of the shared ptys map without consulting PtyOwnership, and the team clipboard takes no workspace argument. Probe: attach to another session's terminal id, and clipboard-copy across sessions. Both must refuse.

P6 — bypassPermissions. The live boot script ends exec claude --permission-mode bypassPermissions. For the owner's own agents that is a deliberate choice. For a stranger's Conductor it means every tool call is auto-approved inside whatever the sandbox permits — so the sandbox is the only boundary, with no second line. Slice 1 should say whether sessions inherit that flag; if they do, P3 stops being one gate among four and becomes the whole of SEC-S.
