SEC-S review — the instantiator design note

Atlas · docs/instantiator-design @ a0bc83e · reviewed before code, against SEC-S · companion to the enforced-vs-conventional audit

Verdict: BLOCK on two, approve the rest. This is a good note and S3 is more honest than most security sections ever get — it says what confinement does not buy, unprompted, and it is right.

It fails SEC-S on one omission and one false premise. Env scrubbing is absent entirely — not a seam, not in the build order, not in the assumptions — and R31 names it as first-slice. And cross-session isolation rests on “the transcripts are in the owner's store partition”, which is not true: the turn store is flat and keyed by terminal id. That second one changes the note's own privacy question, because the exposure is not only owner-reads-caller. It is caller-reads-caller.

Blocking

BlocksB1 · Env scrubbing is not in the note at all

Four axes in SEC-S; the note addresses three. There is no env seam, and “What I will build first” lists neither env scrubbing nor admission control nor per-session budgets — all three of which R31 puts in the first slice by name, for the stated reason that bolting them on later is how the wave-C class happens.

This is not theoretical. Every session terminal spawns through the ordinary path, which does:

env: { ...sanitizeAgentEnv(process.env), TERM_PROGRAM, COOKREW_*, PATH }

sanitizeAgentEnv = drop CLAUDECODE, CLAUDE_PID, CLAUDE_EFFORT, CLAUDE_CODE_*
                   keep everything else, verbatim

A three-key denylist whose own comment says it exists to suppress transcript saving. So a stranger's Conductor is spawned holding the owner's ANTHROPIC_API_KEY, GITHUB_TOKEN, AWS_* and SSH_AUTH_SOCK. The name is the trap — it reads at the spawn site like this box is already ticked.

Wanted before code: a seam beside S3, same shape — envFor(sessionId): NodeJS.ProcessEnv, constructed from {} with an explicit allowlist, never a denylist. Pure, so the mutant list can include “owner's key is set in process.env” and assert it is absent. A denylist cannot be completed and this one is not even aimed at secrets.

BlocksB2 · “The transcripts are in the owner's store partition” — there is no partition

The note leans on this twice: once under “Where it plugs in”, and once in the privacy question. Verified against the tree and the running install:

TurnStore.fileFor(terminalId) =>
  path.join(this.dir, `${safeId(terminalId)}.jsonl`)     // flat

~/.cookrew/turns/<terminalId>.jsonl                     399 files, one namespace
~/.cookrew/checkpoint-annotations/<terminalId>.json      same

No workspace segment, no session segment. S3 confines the sandbox directory; nothing confines the ledger. Every session's conversation and every Sous title lands in one namespace keyed by an id that is not a secret — it is on the canvas and in every IPC payload. loadAll() walks the whole directory, and it is what the board and checkpoint search run on.

This changes the note's own question. It is framed as owner-reads-caller, and all three proposed answers are about what to tell the caller about the owner. The finding here is a fourth thing none of them cover: a caller's Conductor that reaches checkpoint search reads other callers' conversations. That is not a promise to reword — it is a partition bug, and it must be fixed whichever answer the owner picks.

Wanted before code: the partition, named as a seam, with loadAll()'s call sites (board, search, rebuild-diff) enumerated, because the partition changes them. TurnStore is documented as the only reader of these files, which is what makes this tractable now and expensive after the first service ships.

Fix before building, not blocking

FixF1 · The precedent confine() cites fails confine()'s own mutants

S3 says it follows “the same shape as PresetStore.dirFor”. That shape is:

preset-store.ts:70   dir !== root && !dir.startsWith(root + path.sep)
pin-store.ts:45      !file.startsWith(root + path.sep)
mobile-server.ts:540 !file.startsWith(root + path.sep)

An un-normalised startsWith. It is defeated by .. unless the path was resolved first, and by a symlink always. Atlas's own mutant list has “a session id containing ..” and “a symlinked sandbox” — so copying the cited precedent fails his own tests, which is the good outcome, but only if he does not reach for the precedent to make them pass.

Wanted: realpath both sides, then compare, and refuse when the candidate does not exist rather than resolving optimistically. One audited helper, and the three sites above switched to it — they are the only containment checks in src/main and they currently each have their own copy.

FixF2 · confine() is bypassed by an existing renderer-reachable path

S3: “Every terminal in a session gets its cwd through confine.” True at mint. Not true afterwards — moveTerminalCwd sets a terminal's cwd on a different path, reachable from the renderer, and it does not merely permit an outside directory:

if (!deps.store.dirs().includes(target)) {
  if (!deps.dirExists(target)) throw ...
  deps.store.addWorkspaceDir(deps.store.activeId, target)   // enrols it
}

The only check is that the path exists. An out-of-sandbox directory is not refused, it is added to the workspace — the operation widens the trust set. This is the renderer-reachable rmSync traversal family with the twist that a traversal fix does not touch it: it does not read outside the root, it relocates the root.

The note's own sentence is aimed one function too far left — “'we always pass the sandbox dir' is the kind of guarantee this program keeps finding to be decorative.” Exactly right, and the decorative guarantee is moveTerminalCwd, which never calls confine.

FixF3 · “An ordinary resident” is the win and the attack surface, and only the win is written down

Under “Where it plugs in”, a session workspace being an ordinary resident is listed four times as nothing to do — park/drain, CallsInFlight, uniqueSlug, the gate. That is genuinely good reuse. It also means every existing IPC that acts on “a workspace” now acts on a stranger's session, including workspace:dir:add, the cwd move above, and PtyOwnership.claim, which moves a terminal between workspaces with no authorization step (per the audit, it is an index, not a wall).

Wanted: a short enumeration of which existing IPCs become reachable against a session workspace, and what refuses them. Not a redesign — a list, so the reuse is a decision rather than an inheritance.

Approved, and worth saying so

ApprovedS3's honesty, END's ordering, and the pin hash

S3 states its own limit. “It constrains where an agent starts. An agent that runs cd /… is not stopped by a cwd — only by an OS boundary we do not have. So the honest claim is 'a caller's files land in their folder', not 'a caller cannot read yours'.” That is the correct claim, reached without being asked, and it is the sentence I would otherwise have written this review to force. Keep it in the code, not only the note.

END. Reusing CallsInFlight.cancelWhere rather than growing a second cancellation path is right, and “cleanup runs after the cut, never before” is the ordering a teardown gets wrong exactly once. Deleting the sandbox by default is the correct posture — keeping a caller's files is a decision nobody asked the owner to make.

S1c, the pin content hash. Outside SEC-S and I want it on record anyway: two offline machines both cutting “V2” is a real R31-introduced hazard, sync cannot repair it after sessions are running on both, and content-addressing follows PresetStore's existing precedent rather than inventing one. Small now, unpickable after the first service ships. Yes.

On the question he wants ruled

AnswerThe part that is mine

Atlas is right that it is the owner's call and right to want it before S3. One correction to its shape: the choice is between three promises, and B2 means there is a property underneath that has to be fixed regardless. Partitioning the turn store is not option 3 — it is a precondition for any of the three being truthful about callers to each other.

With that separated, my read: option 1 (say it plainly) is the only one that survives hostile QA, because options 2 and 3 both describe a boundary that does not exist and SEC-S's whole premise is enforced-not-conventional. He is also right that option 3 is not a privacy claim; it is friction, and worth doing on its own merits once the partition is real.
