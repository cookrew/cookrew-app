SEC-S — what is enforced vs merely conventional

Audit of the existing confinement primitives (terminal-cwd.ts, pty-scope.ts, pty.ts) ahead of Atlas's instantiator note · Commander · against dev@afb027f

Of the five SEC-S requirements, none are enforced today. That is the expected answer for a feature that has not been built — the useful part is which primitives look like they already help and do not, because those are what a design note will be written on top of.

Two do exactly that. sanitizeAgentEnv is named like env scrubbing and is a three-key denylist for a different purpose entirely. PtyOwnership reads like session isolation and is a bookkeeping index. And one premise stated in the R31 section — “store partitions already separate” — is not true of the turn store.

The two that look like help

Trap1 · sanitizeAgentEnv is not env scrubbing src/main/pty.ts:374
export function sanitizeAgentEnv(env) {
  const clean = {}
  for (const [key, value] of Object.entries(env)) {
    if (key === 'CLAUDECODE' || key === 'CLAUDE_PID' || key === 'CLAUDE_EFFORT') continue
    if (key.startsWith('CLAUDE_CODE_')) continue
    clean[key] = value              // <-- everything else, verbatim
  }
  return clean
}

Its own comment says what it is for: “a launcher-session marker turns off the agent's transcript saving”. It exists to defeat Claude Code's nested-session detection. It is not a secrets boundary and was never claimed to be one.

So every spawned harness inherits the owner's whole environment — ANTHROPIC_API_KEY, GITHUB_TOKEN, AWS_*, SSH_AUTH_SOCK, HOME. Observable on the running fleet right now: the pi processes carry KREWCLI_KREWHUB_URL, BUB_API_FORMAT and INIT_CWD straight through.

For the instantiator: a denylist cannot be completed, and this one is not even aimed at the right target. The env must be constructed — start from {}, add the handful of variables the harness needs, and never enumerate what to remove. The danger is the name: someone reading sanitizeAgentEnv(process.env) at the spawn site has every reason to think this box is ticked.

Trap2 · PtyOwnership is an index, not a wall src/main/pty-scope.ts

It maps terminal id → workspace id so a scope can take a filtered view of one shared PTY map. Its docstring is explicit that the sharing is deliberate — the orphan reaper needs to see every terminal the app owns, and N managers each doing discovery is the O(attached × panes) shape that cost 190ms → 6.85s in August.

Two consequences for sessions:

• claim() moves a terminal between workspaces on demand — that is the cut-and-paste-across-workspaces feature. Under a session model it is a cross-session transfer primitive with no authorization step in front of it.

• The reaper's completeness requirement (allTerminalIdsStrict must see everything) is in direct tension with per-session isolation, and separately with PERF-N: a global inventory is O(resident) by construction. Worth naming in the note before the design assumes both.

The premise that is false

Correction3 · The turn store is not partitioned src/main/turn-store.ts — fileFor()

R31 says “sandbox dirs mutually invisible, store partitions already separate.” Workspaces do get their own directory under ~/.cookrew/workspaces/<id>/. The checkpoint ledger does not:

private fileFor(terminalId) {
  return path.join(this.dir, `${this.safeId(terminalId)}.jsonl`)   // flat
}

~/.cookrew/turns/<terminalId>.jsonl                  399 files, one namespace
~/.cookrew/checkpoint-annotations/<terminalId>.json  same shape

Conversation transcripts and their Sous titles are keyed by terminal id in one flat namespace with no workspace or session segment. Anything that can name a terminal id can read any session's conversation — and a terminal id is not a secret, it is on the canvas and in every IPC payload. A caller's prompt-injected orch agent that can reach a read of this store reads the owner's history and every other caller's.

For the instantiator: partitioning this is not a path prefix bolted on later. TurnStore is documented as the ONLY reader of these files, so the partition can be introduced inside it — but loadAll() walks the whole directory and is what the board and checkpoint search run on, so a partition changes those call sites too.

Confinement: nothing, and it widens

Not enforced4 · moveTerminalCwd takes any path and enrols it src/main/terminal-cwd.ts:60 · ipc workspace:dir:add

The only check on the target is that it exists:

if (!deps.store.dirs().includes(target)) {
  if (!deps.dirExists(target)) throw new Error(...)
  deps.store.addWorkspaceDir(deps.store.activeId, target)   // <-- enrols it
}

There is no containment root. A directory outside the workspace is not refused — it is added to the workspace, so the operation grows the trust set rather than being checked against it. It is renderer-reachable (addWorkspaceDir is on the preload bridge, and the file browser drives the move).

This is the week-one rmSync traversal family, with one difference that makes it worse rather than better: that bug read or deleted outside the root, this one relocates the root. A traversal fix that normalises the path does not touch it.

Every containment check in src/main — all three of them:

mobile-server.ts:540   !file.startsWith(root + path.sep)     static file serving
pin-store.ts:45        !file.startsWith(root + path.sep)     pin store
preset-store.ts:70     dir !== root && !dir.startsWith(...)  preset store

None guard terminal cwd or spawn. And the shape itself is the fragile one: a startsWith on an un-normalised path is only sound after realpath — /root/../etc and a symlink both defeat it. Do not let the instantiator copy this pattern; give it one audited helper and make these three use it.

Structural5 · cwd cannot be the boundary, at any quality of check

Worth stating plainly before the note is written, because it bounds what a review can approve. The thing being confined is a PTY running a shell. The caller types cd ... Validating the cwd at spawn constrains where the agent starts and nothing about where it goes one keystroke later; the same is true of every tool the harness can call, which is the whole filesystem by default.

Confinement therefore has to be OS-enforced — a sandbox profile (sandbox-exec/seatbelt on macOS), a container, or a separate user — and the design note needs to name which, because “the sandbox is the product” is a claim about process isolation, not about a path string. A note that proposes cwd-plus-validation should not pass SEC-S however carefully the validation is written.

END and teardown

Does not exist6 · Nothing destroys anything

releaseWorkspace() returns the ids it forgets — an in-memory index cleanup, no filesystem teardown, and no sandbox directory to tear down. TurnStore.remove() does delete a terminal's ledger and annotations (and is careful about it), so the mechanism for destroying per-terminal durable state exists and is tested; nothing ties it to a session lifecycle.

One ordering hazard to carry into the note: END must destroy the sandbox and the transcripts, and the transcripts currently live in a flat global namespace (§3). Deleting by terminal id from a session that no longer has an authoritative membership list is how a teardown either misses files or deletes a neighbour's.

What is real, and worth building on

EnforcedPrimitives that hold

One live process per terminal across all backends. migrateForeignSession kills a copy of the agent living under another multiplexer before resuming it here. That is a genuine single-instance invariant and the right base for “a session's agents cannot be doubled”.

One holder per terminal. PtyOwnership does guarantee that no scope tears down a PTY another scope is holding. That is real isolation — for teardown only, not for reads.

Atomic write, fail-closed read. RegistryHostSettings writes sibling-then-rename and treats an unparseable trust list as empty rather than degrading permissive. That is the shape a sandbox registry should copy verbatim.

Refuse rather than infer. The lineage walk and the registry host resolution both decline on ambiguity and say why. The instantiator will need the same posture for admission control, and the vocabulary already exists in this codebase.

What I will hold the note to

Concretely, when Atlas's design note lands, these are the questions it has to answer before any code — each one because the audit above shows nothing in the tree answers it today:

1. Which OS mechanism enforces the sandbox, given a shell can cd ..? 2. Is the spawn env constructed from empty, and what is the allowlist? 3. How is the turn store partitioned, and what happens to loadAll()? 4. What authorizes claim() moving a terminal across sessions? 5. What does END delete, in what order, and how does it enumerate membership authoritatively? 6. How does the orphan reaper keep global visibility without becoming a cross-session read — and without being O(resident), which is PERF-N's problem in the same component?
