User-journey audit — the author and the buyer

QA as a real user, not a gate-runner · live system, real input · 2026-08-23 · Magpie

What this is. The eval gates already proved correctness — 25 mutants, FAIL 0. This asks a different question: could a person find these features, and would they understand what they found? A wall is a finding, not a failure. Every verdict below is anchored to an artifact I actually saw.
Methodological caveat, stated up front. I have read this source deeply, so I know things a real user cannot. Where insider knowledge got me unstuck, I have marked it — because that unblocking is itself the finding. Twice during this audit my own knowledge produced a wrong reading, and both are recorded below rather than quietly corrected.

The author journey does not exist in the product. The buyer journey exists as a protocol and is largely correct, but every point where a human must act is either absent or raw JSON.

Person 1 — the author

I built an agent worth selling. I want to export it, publish it, price it, and know where my money arrives. I start where anyone starts: looking at the app.

A1Where do I click to begin?Wall

I enumerated every visible, clickable control in the product chrome — 40 of them. Not one mentions publish, export, sell, price, payout or market. The dock is five icon-only tools.

Artifact — the entire dock, as a user meets it
⟨CLIPBOARD⟩  ⟨TERMINAL⟩  ⟨NOTE⟩  ⟨BROWSER⟩  ⟨CONNECT⟩
top bar: ⟨Refresh the canvas⟩ · Canvas · Board · 🗂Cookrew Dev

The trap I nearly fell into: a document-wide scan does find "Marketplace", "publish" and "price" on this canvas — all of it inside rendered design documents in browser cards. The canvas displays the spec that defines the feature. Scoping to product chrome, the matches drop to zero.

A2Is there a publish path at all?Wall

The app's whole preset/team IPC surface:

preset:list              preset:installed:list        team:save    team:list
preset:installed:uninstall   preset:installed:rotation:*  team:fork    team:clip:*

Install, place, uninstall, save-a-team locally. There is no publish channel, no registry client, and no call to POST /v1/presets anywhere in main or the renderer. The single registry reference is an env var, COOKREW_REGISTRY_HOST, empty by default — and unset on the running app.

My own error, recorded: I first grepped the renderer for the IPC channel string and got zero, and nearly reported "the chips are wired to nothing." Wrong — the renderer calls window.api.listInstalledPresets(); the channel name only lives in the preload. That is precisely the alias blindness I had written a gate against an hour earlier, and I walked straight into it.

A3So how does anything get published?Wall

Only over HTTP, by hand. To publish one priced preset I had to: generate an ed25519 keypair, build a canonical manifest, sign it, run a WebAuthn ceremony for a publish-scoped token, POST once to receive a 401 carrying a countersign challenge, sign that as a second assertion, and POST again with a payout address.

Artifact — what "publishing" costs today
~140 lines of code · 2 cryptographic ceremonies · 2 POSTs · 1 hand-built signature
No human does this. I only could because I had written the crypto helper myself.
A4Where will my money arrive?Wall

The payout address is an API field with no surface. Omit it and publish refuses with the bare token payout_missing. Nothing explains what an EVM address is, or which chain, or that the money never touches Cookrew — a genuinely reassuring fact the author never gets told.

Worth a decision, not just a fix: the address is format-checked only, with no EIP-55 checksum (the source says so plainly and explains why — keccak256 is not in node:crypto). A mistyped but well-formed address passes, and the money goes somewhere unrecoverable. The mitigation the source proposes — catch it at publish time, where the author is standing — is exactly the surface that does not exist yet.

Person 2 — the buyer

Someone sent me a link. I have no app.

B1Open the install link with no appClear

This page is the best thing in the whole journey. It names the preset, the author and the version, says what a preset is, and pre-empts the obvious fear.

Artifact — verbatim visible text
Pro Toolkit
published by @cookrew-seed · v1
A Cookrew preset — a team of AI agents you can place on your canvas.
This preset needs an account before it can be downloaded.
Open this link in Cookrew to place it.
Opening a link installs nothing. Cookrew checks the preset itself and
shows you what it contains, and you decide.
Cookrew is open source. You can get it here: github.com/cookrew/cookrew-app

"Opening a link installs nothing… and you decide" is doing real work. Keep it.

B2…but what does it cost?Wall

I published a preset priced at 2.50 USDC and opened its link. The page is byte-identical in structure to the free one. The price appears nowhere.

Artifact — money tokens in the priced preset's page
visible-text money tokens: ["Price", "Price"]
  → both are the substring inside the preset's NAME, "Priced Toolkit".
raw HTML: no amount, no asset, no chain, no "paid", no currency symbol.

The page warns you about the 401 ("needs an account") and says nothing about the 402. A buyer learns the thing costs money only after installing an app, creating a passkey, and reading a JSON body.

B3"Open this link in Cookrew"Wall

The page's only call to action cannot work. The app recognises install links only for hosts listed in COOKREW_REGISTRY_HOST, which is empty by default and unset on the running app. So a default install recognises no registry at all, and the link does nothing.

This is a deliberate fail-closed posture and the source argues for it well — an app must not learn to trust a host because a page said so. But the consequence is that today the shared link is a dead end for everyone.

B4"needs an account" — how do I make one?Confusing

Nothing on the page, and nothing in the app, creates an account. The passkey enrolment exists only as POST /v1/identity/register. The word "account" also sets the wrong expectation: there is no account, there is a passkey — no email, no password, nothing to recover.

Exactly right as protocol, and the uniform empty body is a deliberate anti-enumeration choice I would defend. For a person who pastes the URL into a browser, it is a blank page.

B6The passkey ceremonyConfusing

It works, and it is fast — 147 ms from challenge to minted token, driven headlessly with a software authenticator. But there is no UI anywhere: no passkey prompt, no Touch ID sheet, no enrolment screen. A real buyer cannot start it. Insider knowledge did the work here — I had already written the ceremony driver.

B7The 402 — what am I buying?Confusing
Artifact — verbatim, the whole thing a buyer receives
{ "terms": {
    "amount": "2.50",
    "asset":  "USDC",
    "chain":  "base",
    "payTo":  "0xfacade0000000000000000000000000000000000",
    "nonce":  "IgORsUXynJ0UEyTKEOoiFE9J5DU14pv_D0lFu9G-gbY",
    "expiry": 1787493905811
} }

The values are complete and correct — price, asset and chain are all named separately, which matters, because a transfer to the right address on the wrong chain is money gone with a successful receipt. Three gaps for a human:

  • expiry is a raw epoch integer. 1787493905811 is unreadable. Nothing on the wire says "you have 15 minutes".
  • Nothing says what the payment buys. It actually buys v1 and every later version — a genuinely good deal that the buyer is never told.
  • Nothing says what happens after. That you will not be asked again is the strongest thing about this design and it is invisible.

By spec this is intentional: bodies carry machine values and the sheet renders sentences. The sheet does not exist, so today the raw JSON is the user experience.

B8The 403 — what do I do about it?Confusing
Artifact — verbatim
HTTP/1.1 403 Forbidden
{"reason":"scope"}          ← no remedy URL, no retry-after (both correct by spec)

Protocol-correct: scope is the one denial a client resolves itself by re-running the ceremony, so a remedy link would be wrong. But the word means nothing to a person, and nothing tells them re-authenticating is the fix. The machine knows what to do; the human does not.

B9PayingWall

There is no wallet sheet. To pay, I base64url-encoded a JSON object by hand and set a header.

Artifact — what a buyer must construct
X-Payment: eyJub25jZSI6InIyNTYtdk9BeWZaZ1AtQnBiZFZVcTJNdm1zazFCbHlmVmhf...
decodes to: {"nonce":"r256-vOAyfZgP-BpbdVUq2Mvmsk1BlyfVh_8pQtJL5c","tx":"tx-dev-ok"}

Expected — the wallet is not built. Recording it as the buyer meets it: the money step is currently a developer-console exercise.

B10After payingClear

This is the part that feels finished. The payment returns the signed manifest, and the next fetch with no payment header at all returns 200. The receipt holds. A buyer is not asked to sign again.

pay      → 200  (signed manifest, author key, blob hashes)
re-fetch → 200  (no X-Payment sent — the purchase is remembered)

Two walls I hit that are not on anyone's roadmap

The remote surface greets you with "Not paired"Confusing

Every pointer event is swallowed by a modal until you pair. The copy is good and the instruction is accurate — I ran cookrew mobile, got a token, and it worked first try. Two notes: it says "not paired any more", so a device silently loses pairing at some point and nothing says when or why; and recovery is pasting a token by hand.

The canvas renders the spec that defines the productConfusing

Not a defect, but it makes the product nearly un-auditable from the outside: any search for a feature name finds the design document describing it. It also means a newcomer opening this canvas sees a dozen browser cards titled "Presets Marketplace — …" and would reasonably conclude the marketplace ships today.

Top 5 — what would make a real person give up

  1. The author journey has no entry point at all. Zero of 40 product controls mention publishing; there is no publish IPC, no registry client. The entire seller side is an HTTP API reachable only by writing cryptographic code. An author cannot begin, and nothing tells them that — they just hunt and stop. Everything downstream is blocked on this: with no author there is nothing to buy.
  2. The shared link's only instruction cannot work. "Open this link in Cookrew to place it" — but COOKREW_REGISTRY_HOST is empty by default, so a default install recognises no install links. The best-written page in the product ends in a dead click.
  3. The app is slow at rest: p50 1.4 s, p95 3.4 s on a 1.2 KB call. This is felt in every single interaction, so it taxes every other fix on this list. The canvas load is a 506 KB single blob on top of it.
  4. A paid preset never says it is paid. The link shows no price; the buyer discovers the cost after installing an app and creating a passkey, as a raw JSON body. That is the worst possible moment and the worst possible format to learn a thing costs money.
  5. Every human decision point is raw JSON. A {} at 401, an epoch integer at 402, the bare word scope at 403, and a hand-built header to pay. The protocol underneath is correct and well-argued — but the sheets that were always meant to turn it into sentences do not exist, so the machine layer is currently the user interface.

What is genuinely good, and should not be lost

  • The install page's trust copy. "Opening a link installs nothing. Cookrew checks the preset itself and shows you what it contains, and you decide."
  • The receipt. Paying once and never being asked again works, survives a restart, and is the single most convincing thing in the money story.
  • Chain named separately from amount. Right address, wrong chain is money gone with a successful receipt; the terms make that impossible to get wrong.
  • The pairing instruction. It told me exactly what to run, and it worked first time.
  • The protocol layer's speed. Sub-20 ms gate decisions, 147 ms passkey ceremony.

Method. Live app on :8643 driven by real input through external CDP Chrome on :9245; registry built from merged dev (5cdb670, M2 included) on :8850 with a priced preset published through the real publish route. No canvas browser was pointed at the app. Latency is 20 samples under the fleet's real load, reported as percentiles, never a mean.

Honesty notes. Two readings in this audit were wrong before they were right — a renderer grep that missed an aliased call, and a "no price anywhere" claim that needed a second look because the preset was named "Priced Toolkit". Both are written into the steps rather than silently fixed. Expected walls (grant UI mid-build, no wallet sheet, localhost registry) are recorded as a user meets them, not excused.
