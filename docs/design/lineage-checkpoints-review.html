C1 — the counter is fixed; the truncation is not Critical

alignToLedger correctly renumbers the incoming run against the ledger. But replaceHistory then replaces the entire history with only that run — the 597 earlier records are never carried forward. alignToLedger already computes the join position at; it throws it away.

Probe result — real TurnTracker, no mocks
after restore:          613
after live reconcile:    16     index range: 598 -> 613
Why it is destructive, not cosmetic

commitReconciled → store.scheduleSave(id, records) marks 'all' dirty, and an 'all' flush treats those records as the whole truth: annotations.save rebuilds the sidecar from them (turn-annotations.ts:602-607) and persistConversation rewrites the file. The 597 die on disk too, along with their Sous titles.

It is the production path, not a synthetic one

session-sync.ts:620 calls this.turns.replaceHistory(terminalId, acc.records()), and the accumulator covers the bound session file only. That is exactly the 16. After this merge Commander gets 16 checkpoints numbered 598–613 instead of 16 numbered 1–16: better numbers, same loss.

Fix shape

Preserve previous[0 … at-1] — the prefix before the aligned run — and concat the aligned incoming. The join position is already known inside alignToLedger; the cheapest correct change is to return it (or the joined array) rather than only the shifted tail. Note the store's 'all' semantics mean a partial history must never reach scheduleSave.

H1 — rekeyByUuid silently overwrites a collided annotation High

A moved annotation and an unmatched one can land on the same target index. next.set(target, annotation) has no collision check, so last write wins.

Probe result
report: {"moved":1,"unmatched":[2]}
titles kept: ['2:TITLE-B']      ← TITLE-A is gone, and the report claims success

Setup: record 1 has a uuid and moves to index 2; record 2 has no uuid, so it is "unmatched" and kept where it is — at index 2. This is precisely the wrong, not orphaned failure the function was written to prevent, occurring inside the function written to prevent it.

Fix shape

Refuse on collision: if next.has(target), leave both where they are and report both in unmatched. Losing one loudly beats moving it quietly — the function's own stated rule, applied to its own output map.

H2 — not idempotent on overlapping ranges; a re-run corrupts High

Probe result — identical arguments both times
first:  {"moved":2,"unmatched":[]}   ['7:TITLE-C', '3:TITLE-E']
second: {"moved":1,"unmatched":[7]}  ['7:TITLE-E']   ← TITLE-C destroyed, TITLE-E on the wrong turn

oldByIndex is keyed by old indices while current now holds new ones. Where the two ranges overlap, a second pass re-resolves through a stale mapping and moves an already-moved annotation again. moved > 0 then persistSnapshots the damage.

The branch's "is idempotent — running it twice changes nothing" test passes only because its fixture uses disjoint ranges (index 400). A rewind — one of the three renumber causes the docstring itself names — produces exactly the overlapping case that breaks. The test's premise is narrower than its claim.

Fix shape

Make the operation self-describing rather than positional: stamp the applied state (or key the sidecar by uuid outright, which is the stated destination anyway), so a second run has a fact to check instead of re-deriving through a mapping that is no longer true.

M1–M4 and the LOWs

M1 — walkRefusals() is module-global Medium

sessionChain is async and assigns lastRefusals only at the end of the walk. Two terminals walking concurrently means a walk that did refuse can report refusals: [] — turning an honest decline into a silent truncation, the exact failure lineage-ledger.ts's own docstring says must not happen. Fix: return the refusals from sessionChain instead of parking them in module state.

M2 — two silent stops in the walk Medium

A missing predecessor file and the MAX_LINEAGE_DEPTH cap both break without recording a refusal. Only the /clear inference reports one. A chain truncated by a deleted transcript is therefore indistinguishable from a complete one — "quietly partial", by the file's own standard.

M3 — the pin refusal does not cover the path that renumbers Medium

Confirmed stated, not hidden — this was review item 4. refuseRenumber is real, well-argued, and correctly wired into planRecovery. But planRecovery is unwired, and the live renumber — alignToLedger inside replaceHistory — shifts indices with no pin check at all. So a node carrying pins is renumbered silently today, which is the thing the refusal exists to prevent. Stated, but narrower than it reads.

M4 — planRecovery has zero tests and no caller Medium

The tool this incident depends on — "planRecovery reproduces it from the transcripts" — has no test file (tests/ gains only lineage-ledger and annotation-rekey) and nothing in src/ imports lineage-recover. The recovery is currently a manual, unproven path.

LOW Low

  • ambiguousOld uses [...oldByIndex.values()].includes(...) per record — O(n²); ~188k comparisons at 613 records, worse on larger histories.
  • oldByIndex.set(record.index, …) silently overwrites on a duplicate index in before; not flagged as ambiguity.
  • Re-running a disjoint re-key reports unmatched: [newIndex] — a false alarm on every re-run (probe B's second run reported unmatched:[7]).

Item 5 — rebuildLedgerInto: not one-line-shaped

Tinker's parting hazard is real and confirmed: rebuildLedger resolves a single harness.watchFile(node) — the bound session only — renumbers from 1, and rebuildLedgerInto scheduleSaves 'all'. Pointed at Commander it would rewrite 613 back to 16.

But it is not a one-line change, and that should not be promised. The blocker is sync/async: sessionChain and readHeadLines are async; rebuildLedger and rebuildLedgerInto are sync. Walking the chain forces a sync → async conversion of both plus their callers.

What is small, sync, and worth doing before merge: make rebuildLedgerInto refuse to write a rebuild shorter than the ledger it would replace. A few lines, no async, and it converts a data-destroying tool into a refusing one — which is this branch's own stated philosophy. The lineage-aware rebuild is a follow-up.

Mitigating: rebuildLedger / rebuildLedgerInto have no production callers today — tests/ledger-rebuild.test.ts only.

What is right, and worth keeping

  • The diagnosis. "The durable record is the truth and the parse is a cache of it that can silently disagree" is the correct framing, and deriving the base from the ledger closes the class rather than the instance.
  • Reading the boundary instead of inferring it. compact_boundary is a fact; /clear is a heuristic; the two are kept apart, and the inferred join is opt-in and refuses on ambiguity, weak overlap, or no candidate.
  • LINEAGE_HEAD_LINES = 256. The reasoning — that 24 read Commander's own edge as absent at lines 26–27 and silently dropped a 119 MB ancestor — is exactly the kind of measured justification this lane should hold.
  • Choosing transcripts over node.sessionLineage because the array is not demonstrably complete, and a partial lineage fails like a wrong one.
  • The uuid identity claim was verified, not assumed: 2,327 checkpoint uuids across 36 agents, ledger vs. rebuild, identical.
