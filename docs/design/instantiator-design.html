The Instantiator

Design note before code · Ruling R30 · Commander · 2026-08-24
First gated call → a WorkspaceSession from the template at its pin, a sandbox workdir, the conversation routed to that session's Conductor.

R30 lands on machinery that shipped. Verified in the tree, not taken from the table: SessionRegistry (get/peek/isLive/resident/drainTick, park + drain), copyTeam (teams.ts:819), VersionPinRecord + nextVersion, per-terminal cwd in pty.ts, and deriveSlug/uniqueSlug. The instantiator is a composer of these, not new subsystems.

What it does, in one path

The seams I will cut

Five, and each is a place I want to be able to test a decision without a filesystem, a PTY or a network. The security-critical one is S3.

S1 · TemplateSource — what a template IS to the instantiator

read(templateId): { snapshot: TeamSnapshot; pin: VersionPinRecord; version: number }

The instantiator must not know how templates are stored. Today that is TeamStore; R30 adds transcripts-at-pin. Behind this seam, "template" is a value — which is also what makes new sessions get the latest pin, running sessions keep theirs testable: the version is resolved once, at mint, and never re-read.

S2 · SessionKey — what identity a session has

keyOf(serviceId, callerSub, ordinal): { sessionId; slug; workspaceName }

The demo shows ana-1 and ana-2: one caller, two sessions, different versions. So the key is not (service, caller) — it is (service, caller, ordinal), and "does a session exist" is really "does an OPEN one exist". Pure, so collisions and slug uniqueness are tested without creating anything.

S3 · Sandbox — the security-critical one

rootFor(serviceId): string
dirFor(sessionId): string
confine(candidate: string, sessionId): string | null   // null = refuse

Every terminal in a session gets its cwd through confine, which resolves and refuses anything outside the session dir — the same shape as PresetStore.dirFor, which already refuses a path that would leave its store. A function, not a convention: "we always pass the sandbox dir" is the kind of guarantee this program keeps finding to be decorative.

What confinement does NOT buy, stated now rather than discovered later. It constrains where an agent starts. An agent that runs cd /, or a tool with an absolute path, is not stopped by a cwd — only by an OS boundary we do not have. So the honest claim is "a caller's files land in their folder", not "a caller cannot read yours". Tinker should review this seam specifically, and the caller-facing copy must not over-promise.

S4 · SessionLifecycle — END, and what it cuts

end(sessionId, reason): { stopped: number }

END is the panic button and stops mid-call — which is the revoke semantics already built and proven: CallsInFlight.cancelWhere cuts the running call, the reply never reaches the caller even if it resolves a beat later, and the wire says 403. END reuses that seam rather than growing a second cancellation path. Cleanup runs after the cut, never before: deleting a sandbox out from under a running agent is how a stop becomes a crash.

S5 · ConductorRoute — one door

conductorOf(sessionWorkspaceId): terminalId | null

Only the orch agent answers. This deletes the per-agent grant matrix for services — and it also supersedes the per-conversation fork: under R30 the session is the isolation, so there is one workspace, one Conductor, and no cutVersion per conversation. call-session.ts's fork discipline stays for Door B (remote teammate) and is not used here. Worth stating because the two paths now diverge and someone will otherwise wire the fork in out of habit.

What I will build first

  1. S2 + S3 pure — keys, slugs, and confine, with mutants: a session id containing .., an absolute cwd, a symlinked sandbox, two callers colliding on a slug.
  2. Mint against a temp dir — real copyTeam, no PTYs.
  3. Route + END — first call creates, second reuses, END cuts mid-call.

No renderer work: the Sessions table is Fresco's, and it reads facts this produces.

The one question I want ruled

Under R30 the owner can read every caller's session. What do we tell the caller?

The serve sheet says "You see who's on, never their data." Under R29 that was true by construction — the buyer downloaded a copy and their work stayed on their machine. R30 inverts it: the session is a workspace in the owner's app, on the owner's disk, driven by the owner's PTYs. The transcripts are in the owner's store partition; the sandbox is a folder in the owner's home; the owner can open the workspace and read it. Nothing in the design prevents this, and I do not think anything can — it is the same machine.

So the sentence is not a property, it is a promise, and it is currently on a screen we are asking strangers to trust. Three ways out, and this is the owner's call, not mine:

  • Say it plainly — "this crew runs on its author's machine; they can see your conversation." Honest, and it may be a fine trade for many services. Costs the sentence.
  • Narrow the claim — "Cookrew never sends your conversation anywhere else", which is true and is a different, smaller promise than the one now shown.
  • Make it partly true — session workspaces excluded from the owner's switcher and their transcripts not indexed into the owner's search. Real friction against casual reading; no defence at all against an owner who wants to look. I would not ship it as a privacy claim.

I need the answer before S3, because it decides whether the sandbox is a containment boundary or merely a tidiness one — and that changes what I build and what Tinker reviews it against.

Two smaller things I will assume unless told otherwise

  • END deletes the sandbox. The demo says cleanup on END. I will make deletion the default and log the path, because a caller's files are the caller's and keeping them is a storage decision nobody asked the owner to make. If ended sessions should be recoverable, that is a different feature and I would rather it be asked for than assumed.
  • A parked session keeps its sandbox. Park is not end — the demo shows a session parked two hours and still listed, so parking must cost storage and nothing else.
