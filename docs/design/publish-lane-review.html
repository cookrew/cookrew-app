High

HighH1 · The payout verification never runs src/shared/eip55.ts

checkPayoutAddress has no caller anywhere in src/. The commit is titled “publish verifies the payout address instead of checking its shape”; preset-publish.ts contains no address handling at all.

The module header states: “Validation today is format-only — 0x plus 40 hex — which accepts every single-character typo an author can make.” That describes a codebase this is not. There is no payTo, no payout field, and no 0x…{40} regex outside eip55.ts itself. The 118 lines of tests pass because they call the function directly.

Building the checker before the field it guards is defensible sequencing. Asserting in the commit message and the header that publish is verifying is not: whoever adds the payout field later will find this module already written and tested, and the cheapest reading is that it is already in force. That is how a check that never runs survives — this lane has produced three of those already.

Ask: either wire it at the point the address is accepted, or restate both the commit subject and the header as groundwork and name the lane that must call it.

HighH2 · The dead end is still a dead end src/shared/registry-host.ts · src/main/index.ts:1928

Commit 248e5fd is titled “the empty registry host stops being a dead end without becoming a default.” The half that stops it being a dead end is the refusal text — and it is never shown. registryHostRefusal is defined at index.ts:1928 and referenced nowhere; registryHostHelp has no other caller; recognisesHost is exported and unused.

The live path is unchanged: presetIdFromInstallUrl(url, registryHosts()) returns null on an empty list, exactly as before, and the user sees the same nothing that Magpie hit. The “never a silent default” half did land and is correct; the “never a dead end either” half is written but not connected.

HighH3 · “Reachable without an environment variable” is not reachable src/main/registry-settings.ts

RegistryHostSettings.add and .remove have no IPC channel and no caller. Only list() is consumed. So the settings file is read, but the only way to write it is to hand-edit ~/.cookrew/registry-hosts.json — which is a strictly worse configuration mechanism than the environment variable this commit exists to replace, since it is undocumented and unvalidated.

The module header’s premise — “an environment variable is a configuration mechanism for whoever launches the process, which on a packaged app is nobody” — is exactly right, and it is still true after this branch.

MediumM1 · ~1 in 3,700 addresses can never be published, and the fix offered is the input src/shared/eip55.ts:112

An address whose canonical EIP-55 form happens to be all-lowercase — every letter landing on a hash nibble under 8 — is indistinguishable from an unchecksummed paste, so it is refused as unverifiable-case. The refusal carries a suggestion produced by toChecksumAddress, which for these addresses is byte-identical to what was just rejected. The author is told to paste the mixed-case form “suggested below” and the suggestion is the string they pasted. There is no form of their address that passes.

Found by search, not by argument:

0x0a7384019ee13ed132e70549512345383e6e9e01
  → { ok: false, reason: 'unverifiable-case',
      suggestion: '0x0a7384019ee13ed132e70549512345383e6e9e01' }
  suggestion === input:  true

measured rate: 54 / 200,000 random addresses  ≈  1 in 3,704

The all-lowercase refusal itself is a defensible ruling and I would keep it. The defect is that the branch it lands on cannot detect its own no-op. At minimum: when suggestion === candidate, say so — that this address carries no case information because its checksum form has none, and offer the mixed-case-uppercase round trip or an explicit acknowledgement path. Silently handing back the rejected string reads as a product bug and will be reported as one.

MediumM2 · A malformed host is dropped in silence src/shared/registry-host.ts:57

parseHosts filters entries failing HOSTNAME_RE and reports nothing. The likeliest owner mistake is a scheme:

COOKREW_REGISTRY_HOST=https://registry.example.com
  → parseHosts → []  → source: 'none'
  → "No registry host is configured … or set COOKREW_REGISTRY_HOST"

The owner set it. They are told to set it. This is the same shape as the dead end the sibling commit exists to remove, arriving through the validation path instead of the empty one. Strict parsing is right; discarding without a word is not. A refusal that names the rejected entry and why costs one string.

MediumM3 · recognisesHost lowercases the candidate but not the list src/shared/registry-host.ts:112

recognisesHost does host.trim().toLowerCase() and matches against resolution.hosts verbatim. parseHosts does not lowercase, so an env value of Registry.Example.Com is stored cased and never matches anything. (RegistryHostSettings.add does normalise, so the two configuration routes disagree about the same host.)

Latent today in both directions: the function is dead (H2), and the live comparison in presetIdFromInstallUrl lowercases both sides. It fails closed, so it is a lockout rather than a bypass. Flagged because it is the exported predicate — the next caller inherits it, and registry-host.test.ts has no mixed-case case to catch it. Normalising inside parseHosts fixes both routes at once.

Low

LowL1 · toChecksumAddress assumes a prefix it does not check src/shared/eip55.ts:69

address.slice(2) is safe for every internal call (all post-ADDRESS_RE), but the function is exported. Given a bare 40-char hex it silently drops the first two digits and returns a well-formed, wrong, 38-digit address. For a money helper, reject rather than slice.

LowL2 · burn-address means only the zero address src/shared/eip55.ts:98

The reason code and message are general; the test is /^0x0{40}$/i. Commonly pasted holes such as 0x…dEaD pass as ordinary addresses. Reasonable to scope deliberately — worth naming in the comment so it is not read as covering burns generally.

LowL3 · 0X… is reported as malformed src/shared/eip55.ts:31

All three regexes require a lowercase 0x. An uppercase prefix is a paste artefact, not a malformed address, and the message (“must be 0x followed by 40 hexadecimal characters”) will read as wrong to someone looking at 40 valid hex characters.

On the shape of this branch

Both commits are well-reasoned and the comments are the good kind — they explain the ruling, not the syntax, and the “cannot verify does not resolve to accept” passage is worth keeping verbatim wherever this ends up. The crypto is sound and I would not ask for a dependency instead; the vendoring rationale about shared node_modules across linked worktrees is real.

The single systemic note: every finding above the Medium line is the same one. Four new modules, 876 lines, four test files — and the two behaviours the commit subjects promise are both unreachable from the product. The tests pass because they test the units directly, which is exactly the failure mode this codebase has been paying for all week. A test that calls checkPayoutAddress proves the function works; nothing here proves publish calls it, because publish does not.
