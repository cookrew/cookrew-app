The Instantiator — architecture note

M-C, the load-bearing milestone · SEC-S ships in slice 1 · Commander · 2026-08-24
For Tinker's review before code. Every mechanism below was run on this machine; the commands are inline so the review can re-run them rather than take my word.

THE CORE ALREADY EXISTS. This note is about a WRAPPER. workspaceFromTemplate() — teams.ts:728, "FEATURE 1: create a workspace from a saved team TEMPLATE" — already does the thing I was about to design: it calls forkTeam with fromSavedTeam, retargets the whole snapshot to one directory, and native-restores each terminal's session in the fresh project dir. cookrew workspace create --team has been driving it in production.

So the instantiator is not a from-scratch build. It is gate + sandbox + per-account keying + admission control wrapped around a call that already works. My earlier note proposed composing copyTeam myself; that was reinventing forkTeam one layer down, and this correction cuts the estimate hard.

Also already there: SessionRegistry (park/drain, residency), CallsInFlight.cancelWhere (the proven mid-call cut END reuses), deriveSlug/uniqueSlug. What is genuinely new is confinement, env scrubbing, admission — and one seam, below.

1 · First gated call → a session (wrapping, not building)

onGatedCall(serviceId, accountId, text):
  admit(serviceId, accountId)              // NEW  §5 — refuses BEFORE anything is created
  session = openSessionFor(serviceId, accountId)          // NEW  §4 keying
         ?? await workspaceFromTemplate(   // EXISTS  teams.ts:728 → forkTeam
              sessionDeps(sandboxDir),     // NEW  §2 confinement, §3 scrubbed env
              { name: session.workspaceName,
                dir:  sandboxDir,          // the sandbox IS the target dir — no new plumbing
                team: template.savedTeamName })
  route(conductorOf(session.workspaceId), text)           // NEW  §1b one door

Four lines of the five are new; the one that does the heavy lifting is a call that already ships. forkTeam brings fresh ids, remapped cables, per-terminal working directories and native session restore with it — none of which I should be writing.

The sandbox needs no new plumbing. workspaceFromTemplate already takes a target dir and forkTeam already threads per-terminal cwd through planTeamFork → resolveTerminalContext. Pointing that dir at the session's sandbox is the whole integration. Confinement (§2) is then enforcement on top of a path the machinery already respects, rather than a new concept pushed through it.

Only the Conductor is addressable. conductorOf(sessionWorkspaceId) is the sole resolution; there is no path from the wire to a non-orch terminal. This also supersedes the per-conversation fork for services — the SESSION is the isolation, so no cutVersion per conversation. Door B keeps the fork; the two paths now diverge and the fork is the habit.

1b · The pin does not exist yet — an M-A gap, and it blocks the promise

Confirmed: SAVE cuts no version pin. team:save → teamSaveTracked, and a search for cutVersion, VersionPinRecord, nextVersion or a pin store across teams.ts, team-actions.ts and team-clip.ts returns nothing. The Chief's reading is right.

So "template = workspace at a pin" is not true today: SAVE stores a snapshot with no version identity. Everything R30 hangs on that identity — new sessions get the latest pin, running sessions keep theirs, "tap V1 to see exactly what ana is talking to", "the pin IS the contract" — has nothing to point at.

The instantiator can be built and tested before the pin exists (a session can pin a snapshot id), but the VERSION PROMISE cannot be honoured until M-A cuts one. I would rather that ordering be explicit than discovered when the first V2 lands and every running session silently follows it.

2 · Confinement — naming the actual mechanism

The ruling is right that cwd is not a jail. A cwd says where a process starts; it stops nothing. The mechanism I propose is macOS Seatbelt via sandbox-exec, and I ran it before proposing it. 

(version 1)
(deny default)
(allow process-exec process-fork signal)
(allow sysctl-read mach-lookup mach-priv-task-port)
(allow file-read*)                                     <-- see the asymmetry below
(allow file-write* (subpath "/private/…/sandbox/<session>"))
(allow file-write-data (literal "/dev/null") (literal "/dev/stdout") (literal "/dev/stderr"))

1 WROTE-INSIDE   ·   2 BLOCKED-VIA-CD   ·   3 BLOCKED-OWNER-HOME

Run on this machine: a write inside the sandbox succeeds; cd ../.. followed by a write is refused; a write into ~/.cookrew is refused. The exact attack the ruling names — a child that does cd .. — does not escape.

Two traps found while testing, both of which would have shipped.
  • Symlinked roots silently void the profile. My first profile used /tmp/… and blocked everything, including the sandbox itself, because macOS resolves /tmp → /private/tmp and a subpath is matched after resolution. A profile written against an unresolved path does not fail loudly — it fails as "the agent cannot write anywhere", which reads as a broken agent, not a broken rule. Sandbox paths must be realpath-resolved at mint and the resolved value stored.
  • sandbox-exec is deprecated by Apple and has been for years, while remaining present and in wide use. It is the right choice today and the wrong thing to have only one of: the profile belongs behind a Confinement interface with a named implementation, so a second one can be added without touching the instantiator.

The structural finding: where the wrapper must attach

Wrapping the attach would sandbox the wrong process. PtySession does not spawn the agent directly. It calls activeMux.ensureSession(spec) — which CREATES the tmux/herdr session the command runs in — and then attachSpawn(spec), which returns a command that merely ATTACHES to it. Sandboxing the attach confines a client; the agent stays a child of the multiplexer server, which is the owner's, unconfined, and shared with the owner's own terminals.

So session terminals must not share the owner's multiplexer server. Either the session gets its own server (started, once, under the profile) or session terminals bypass the multiplexer and spawn directly. This is a slice-1 decision because retrofitting it means re-parenting live agents.

The asymmetry Tinker should push hardest on

Writes are confinable today. Reads are not, cheaply. The profile above allows file-read* because the toolchain needs it — node, git, the harness binary and their libraries read from all over the filesystem. Denying reads means enumerating every path the toolchain touches, which is brittle in the direction that breaks the agent, and a wrong entry surfaces as an unrelated failure days later.

So as designed, a caller's agent cannot write outside its sandbox and can read the owner's files. SEC-S says "no cross-session reads: sandbox dirs mutually invisible". Mutual invisibility between sessions is achievable cheaply — deny-read on the sibling sandbox root is a small, stable allowlist. Invisibility of the owner's files is the expensive one. See the question at the end; it is the same question I raised on R30 and it is now concrete enough to cost a number.

3 · Scrubbed env

pty.ts spawns with { ...env, ...spawnSpec.env } — today that inherits the owner's environment. A session's harness must get an allowlist, never the owner's env minus a denylist: a denylist is a list of the secrets we thought of, and the next SDK's variable is not on it. 

sessionEnv(session) = {
  PATH, HOME=<sandbox>, TMPDIR=<sandbox>/tmp, SHELL, LANG, TERM,
  COOKREW_SESSION=<id>,
  …explicitly granted model credentials, if the ruling allows a service to spend the owner's
}

HOME points at the sandbox, which does more work than it looks: it is what stops a harness finding ~/.cookrew, ~/.aws, ~/.ssh or its own config by the usual route, and it makes the sandbox the natural place for the agent's state rather than a place it has to be forced into.

An open consequence the ruling should see: a scrubbed env has no model API key, so a caller's agents cannot run at all unless the owner's key is deliberately passed in. That is the right default — a stranger's prompts should not silently spend the owner's tokens — but it means "serving" implies "lending your API key", and the per-session budget in §5 is what makes that survivable rather than optional.

4 · Keyed by account (R31)

keyOf(serviceId, accountId, ordinal) → { sessionId, slug, workspaceName, sandboxDir }

Account, not credential-sub, and the reason is correctness: a sub is per-enrolment, so the same person on a second device is a different sub and would silently get a fresh session and lose their work. The ordinal is required by the demo's own table — ana-1 on V1 and ana-2 on V2 at once — so "does a session exist" means "does an OPEN one exist". Pure and filesystem-free, so .. in an id, a hostile account name and two accounts colliding on a slug are unit tests.

5 · Admission control and per-session budget — same slice

Both in slice 1, per the ruling, and both are refusals rather than throttles.

LimitRefusalWhy a refusal and not a queue
Concurrent sessions per service503 + honest "full" A queue on a machine that may be a laptop is a promise we cannot keep; "full, try later" is true.
Sessions per account429 Stops one account minting workspaces until the disk is gone — the cheapest denial-of-service here.
Per-session turn/token budget402 or END The owner's key is being spent. R12 already charges per turn; this is its ceiling.
Sandbox bytesrefuse the write path Disk is the resource a stranger can exhaust fastest, and it is the owner's disk.

Admission runs BEFORE mint, so a refusal costs no workspace, no directory and no PTY. A cap checked after creation is a cap that has already spent what it was protecting.

6 · END destroys the sandbox

end(sessionId, reason) → { stopped: number }
  1. cut in-flight        CallsInFlight.cancelWhere — the proven mid-call cut
  2. stop terminals       the session's own multiplexer server dies with it
  3. release residency    SessionRegistry drops it; park/drain unchanged
  4. destroy sandbox      realpath-checked, refuses any path not under the service root

Order matters and step 4 is last. Deleting a sandbox under a running agent turns a stop into a crash, and a crash is where partial state lives. The deletion re-resolves and re-checks the path rather than trusting the one stored at mint — the renderer-reachable rmSync traversal found in review week one is the family SEC-S tells us to assume exists, and a delete is exactly where that family bites.

Slice plan

  1. Pure — keys, slugs, confine(), profile generation, env allowlist, admission decisions. Mutants: .. in a session id, an absolute cwd, a symlinked sandbox root, an env var that must not survive, two accounts colliding, a cap that must refuse before mint.
  2. Confinement, for real — spawn under the profile in a temp root and assert the three proofs above as a TEST, not a note. Includes the multiplexer decision.
  3. Mint + route — real copyTeam from a local pin, Conductor answers.
  4. END — cuts mid-call, destroys, and cannot be pointed outside the service root.

The one question I want ruled — the gate↔forkTeam seam

forkTeam ends by calling deps.switchWorkspace(meta.id), and that switch is not cosmetic — the deps comment says "the switch BOOTS the forked terminals". So the mechanism that already works is coupled to making the new workspace active in the owner's app.

Used as-is, every stranger's first call yanks the owner's screen to that stranger's workspace. Ten callers in a morning is ten hijacks, and the owner cannot work. This is the one place the existing call does not fit the new caller, and it is the seam I want ruled because all three ways out have different costs and only one is mine to choose.

  • Separate BOOT from FOCUS (my recommendation). Add an explicit bootTerminals(workspaceId) to TeamForkDeps; the owner's path passes one that switches, the session path passes one that boots without focusing. The codebase already knows these are different things — copyTeam's own comment says "the view does NOT switch… terminals boot on activation" — it has simply never needed them apart. Small, and it makes the coupling explicit rather than incidental.
  • Pass a no-op switchWorkspace and boot elsewhere. Cheapest to write and the worst to own: forkTeam would then return a workspace whose terminals are not running, and every future caller of it inherits a silent precondition. This is how a function acquires a second, undocumented contract.
  • Let it switch. Only defensible if session workspaces are never really "in" the owner's app — which contradicts R30's whole framing and the Sessions table.

The ruling I want: may I add bootTerminals to TeamForkDeps and have forkTeam call that instead of switchWorkspace, with the owner's existing path passing a switching implementation so its behaviour is unchanged? It touches a function cookrew workspace create --team depends on, which is why I am asking rather than doing.

Everything else in this note I can build as written. Two questions remain open from earlier and neither blocks slice 1: whether confinement is a WRITE or a READ boundary (§2 — write is proven and is my slice-1 recommendation), and the caller-facing privacy sentence that follows from it.
