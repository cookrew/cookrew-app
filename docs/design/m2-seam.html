M2 seam — where payment attaches to the M1 gate

Forge · 2026-08-22 · design only, no implementation. Written while feat/registry-m1 (da1bd2f..8a64348) is under Tinker's review, so nothing here has been built and nothing here should be built until that verdict lands.

no codespec §2 · §4R5 · R11 · R12 · R24 · R26

The purpose of this note is to make M2 a small change. M1 was built so that payment is one added variant on one function, and the value of that claim depends entirely on it still being true when someone tries. So this names the exact attachment point in the code as it stands after A3, the wire shape of the terms, the rules the call path imposes, and where our responsibility ends and the facilitator's begins.

1Where the 402 attaches

One function: registry/src/authorize.ts. It is the only place an answer is chosen — routes never decide anything — so M2 adds a variant and a branch and touches no route, no header plumbing, no client retry loop, and no log. 

// registry/src/server.ts — the Verdict type, as it stands after A3
export type Verdict =
  | { code: 200 }
  | { code: 401; challenge: string }
  | { code: 403; reason: string }
  | { code: 404 }
  | { code: 402; terms: Terms }        // ← M2 adds exactly this

And the decision ladder inside makeAuthorize(). The order is fixed, each step answers before the next runs, and 402 goes between entitlement and serve — after we know who they are and that their credential covers this request, before any bytes exist to hand over.

Two things about that placement are not arbitrary and should survive review.

  • 402 sits after scope, not before. R26's scope refusal is a statement about the credential; a wrong-scope token is not a payment problem, and answering 402 to one would invite a buyer to pay for something the payment cannot fix. Scope was ruled after the original ordering was written, so this is a real insertion decision, not a restatement.
  • 402 sits before serve, not at the route. The route reads verdict.code !== 200 and answers; it does not know what payment is. Keeping the decision in one function is what makes "M2 changes the reason a request is refused, never the machinery" true rather than aspirational.
// registry/src/authorize.ts — the branch M2 inserts, in place
    if (claims.scope !== 'download') return { code: 403, reason: 'scope' }

    // M2: entitlement is real from here. The M1 line below is the seam.
    const held = entitlements.of(claims.sub, presetId)
    if (held === null) {
      const proof = request.headers['x-payment']
      if (proof === undefined) return { code: 402, terms: facilitator.quote(presetId, claims.sub) }
      // Settlement verified → entitlement minted → fall through to serve.
      // NOT a redirect and NOT a second endpoint: the client retried the
      // same idempotent GET, so success here simply continues to 200.
      if (!facilitator.settle(proof, claims.sub, presetId)) {
        return { code: 402, terms: facilitator.quote(presetId, claims.sub) }
      }
    }

A failed settlement answers 402 again, never 403

402 is caller-recoverable and 403 is not — that is the whole reason the codes bind cleanly (spec §2), and D4/R9's rule that a client never loops on 403 depends on it. A proof that did not settle means the payment did not happen, which is exactly the state 402 describes. Answering 403 would tell the client to stop trying and send the buyer to an author who cannot help. The nonce is what stops this becoming a loop: each 402 carries a fresh one, and a spent one is refused.

2The terms payload, on the wire

Spec §2 fixes the shape as x402-style terms. Every field is a machine value; per R14 none of them is a sentence and none of them renders raw — Velvet's mkt.pay.* strings own every word the buyer reads, and they interpolate from exactly these. 

HTTP/1.1 402 Payment Required
content-type: application/json; charset=utf-8

{
  "terms": {
    "price":  "12.00",                        // decimal string, never a float
    "asset":  "USDC",
    "chain":  "base",
    "payTo":  "0x…",                          // the AUTHOR's address, not ours
    "nonce":  "…",                            // single-use, bound to (identity, preset)
    "expiry": 1766000000000                   // epoch ms; the sheet counts down (mm:ss)
  }
}

The nonce should reuse A3's bound-challenge machinery, not invent a second one

A3 (8a64348) already built exactly this shape for countersignatures: Map<value, { exp, binding }> in identity.ts — a nonce that is single-use, expiring, and remembers what it was issued for, checked against the server's own record rather than anything the request claims. A payment nonce needs the same three properties with binding = (identity, presetId).

Reusing it is not just less code. The A3 review found that two operations sharing one unbound payload is a replay; a second, subtly different nonce system is how that class of bug comes back. If the binding string gains an operation tag — 'purchase' alongside 'publish' and 'key-rotation' — the existing wrong-binding refusal covers payment for free.

3The retry, and why there is no /v1/pay

The client pays, then retries the same idempotent GET carrying X-Payment. There is deliberately no confirm endpoint, and this is already a promise the running server makes out loud — /v1/health declares it: 

"notServed": { "/v1/pay": "never — M2 mounts 402 on the manifest gate itself" }

That declaration ships today so nobody builds fixtures against a route that will never exist. Recovery is free by construction: a crash mid-flow retries into 200 (entitlement already minted) or a fresh 402 (payment never landed). There is no third state to reconcile, because the server holds no half-finished purchase.

4The call path is not a payment surface

This is the part most likely to be got wrong by someone implementing from the status-code table alone, because the table describes the download gate and the call path plays by different rules.

RuleWhat it means for M2Already in code
R5 Pay-per-call is a prepaid balance bought at install or top-up. The call path answers 200 or 403 only. 402 never appears mid-conversation — it lives on the chip, install and top-up surfaces. isCallPathAnswer()
R11 A dry meter is balance_empty — a first-class 403 reason, never a seat_limit variant and never the unknown fallback. It is the one 403 whose remedy stays inside Cookrew: top-up on the chip, never a wallet over the conversation. FORBIDDEN_REASONS
R12 Drawdown is per turn, charged at accept — before any work — and the gate never interrupts a running turn. So a balance is checked once per turn, at the boundary, and balance_empty can only surface between turns. DRAWDOWN_CONTRACT

R12's ordering is what makes Velvet's line "its last answer completed · nothing was lost" true by construction rather than by copy. Charging at completion, or re-checking mid-turn, would both create exactly the state that sentence denies. The constant in src/shared/preset-manifest.ts records it so the shape cannot drift before the call path exists; if the contract ever changes, the string must change with it.

Three things M2 must not do, each already enforced by M1

  • HEAD must never answer 402. R3's update check is a HEAD, and R24 says a background check cannot raise a sheet — updateCheckOutcome() already returns silent for every non-200. A 402 on HEAD would mean opening the dock could ask a buyer for money.
  • No wallet sheet over a terminal card. R5, and Magpie already holds it as an interaction gate. The exhausted-meter case is an inline notice whose action opens the balance sheet on the chip.
  • The local entitled flag is never authority. install.json is a cache of the gate's last word (preset-local-state.ts says so in comments today). When the gate is real, a 403 overrides it, and nothing may treat a local true as a licence.

5The facilitator boundary

The registry does two things with money and neither involves touching it: ask for terms and ask whether a proof settled. Everything else — chain RPC, transfer construction, confirmation depth — is the facilitator's, and none of it belongs in a process whose other job is serving signed bytes.

RegistryFacilitator
Issues termsrelays, adds the nonce bindingprices, names payTo and chain
Holds fundsnevernever — buyer pays the author
Holds keysneverits own attestation key only
Verifies settlementasksanswers; marks the nonce spent
Mints entitlementyes, on a verified receiptno
Can alter served bytesno (A5)no

The receipt is (identity, preset, nonce, tx) and the facilitator marks the nonce spent at entitlement mint. That binding is what makes a proof non-transferable: a gifted or resold proof names somebody else's identity and fails.

What a compromised facilitator actually costs — stated precisely, because "trusted" is too blunt

A facilitator that lies about settlement can mint entitlements nobody paid for. That is a loss to authors, and it is real. What it is not is a safety failure for buyers: it cannot alter a preset, because the client verifies the author's signature and content hashes itself (A5), and it cannot forge attribution, because publishing needs a countersigned WebAuthn ceremony it has no part in. So the blast radius of the money component is bounded to money.

This is the same shape as the transparency log's stated limit, and it should be written down the same way: a boundary that is described accurately gets trusted accurately. The registry compromise story is "can only deny"; the facilitator compromise story is "can only give away".
