1 · fix/slug-seat-routes3ad81aa → merged 8e271e5 merge-with-fix

“a slugged phone is a seat, not a reader” — the one auth surface in the queue.

The question that mattered No auth widening, and a phone scoped to workspace A cannot drive a terminal in B. The slug surface is strictly a subset of what the unslugged path already allowed with the same credential.

Evidence chain, in the order it has to hold:

  • The gate sits before handleMobileApi (mobile-server.ts:625-639): allow-list → nodeIdOfRoute → nodeInScope → 404.
  • store.ownerOf (store.ts:849) resolves across all workspaces — active first, then each inactive workspace's persisted state. An unknown node yields undefined, which is false when scoped. Fails closed.
  • Unslugged (scope === null) there is no workspace filter at all: /api/terminal/<any-id>/raw reaches the global PtyManager (index.ts:147) for any resident workspace. So this branch adds a gate where a 501 stood, and removes none.
  • Auth untouched — mobile-api.ts:242 still 401s every non-GET without the pairing token.
  • Normalization order is right: new URL() resolves .. before the slug split, and %2F stays encoded so [^/]+ cannot widen.

The /fork hole is real and stays closed. /api/terminal/:id/fork and /api/team/fork are absent from both tables → 501. The reasoning holds: forkTerminal places the new node via focused-workspace state, so a membership check on the source proves nothing about the destination.

MED /cwd was allow-listed as node-scoped but is focus-bound

ops.setTerminalCwd → moveTerminalCwd reads store.node(id) (store.ts:558 — focusedState.nodes.find), store.dirs() (store.ts:431), activeId = store.focusedId, and validates against this.focusedState.dirs (store.ts:481).

So when the scoped workspace is not the focused one, a phone on /A/api/terminal/<A-terminal>/cwd passes the membership gate and then gets 400 "Not a terminal node" for a terminal that plainly exists in A. Not exploitable — it fails closed in the dangerous direction — but it is exactly the /api/workspace shape the file's own doctrine says disqualifies a route, and it breaks the “correct by construction” claim made for everything in NODE_ROUTES.

Resolved: commander removed /cwd from NODE_ROUTES before merging (6b475ae), back to an honest 501, with a test pinning both scopedRouteSupported === false and nodeIdOfRoute === null.

LOW the anti-drift test's heuristic is narrower than the invariant

nodeShaped filters on source.includes('[^/]+'). A node-addressed route added to SCOPE_AWARE directly with (.+) or ([\w-]+) is node-shaped, wouldn't be caught, and nodeIdOfRoute would return null → ungated. The drift the test exists to catch can still walk past it.

LOW dead query-string alternations hide an asymmetry

/turns(?:\?.*)?$/ and friends can never see a ? — the gate is fed url.pathname. Harmless now, but /raw and /resize have no such alternation, so feeding the gate pathname + search would 501 those two while /turns kept working.

3 · fix/event-query-bounde7d2314 → fixed c11b7ab merge-with-fix

“the metrics query stops growing with the log” — and then says when it's showing a slice.

The central claim holds: the server genuinely supports limit (main/event-log.ts:53, :183-187). Over-fetching by one is a clean truncation detector and createCoalescer is correctly trailing-edge.

HIGH the silent truncation the branch warns about is what it shipped

applyLimit's own comment: “Exposed rather than swallowed: a panel showing metrics over 'all' while silently holding the newest 2000 is a wrong answer that looks right.” The only caller swallowed it. MetricsPanel used useEventQuery — which discards truncated — set no limit, and derived its counts, its timed-event tally and its P50/P95/P98/MAX from the capped list.

Not hypothetical: the owner's session was measured at 3170 events against a 2000 cap, so “all time” already reported percentiles over the newest 63% of the range while labelled as the whole of it.

Fixed: the panel reads the flag and states the cap next to the numbers the cap applies to — a banner, a (capped) marker on the header count, and “in this slice” on the LATENCY tally. useEventQuery keeps working for callers that want the array alone, but now documents that reaching for it around a rollup is how this happened.

MED the two query paths disagreed about which end was newest

applyLimit trims by slicing the tail — correct only against an oldest-first list. The server serves oldest-first and limits by keeping the newest. queryEvents documented the opposite and its mock branch sorted descending, so the fallback returned the oldest N while reporting a truncation: the right count, trimmed off the wrong end, in the one mode with no server to contradict it. The mock also ignored limit entirely.

Fixed: the mock mirrors main/event-log.ts exactly, limit included.

// before                          // after
sort((a,b) => b.timestamp - a.timestamp)   sort((a,b) => a.timestamp - b.timestamp)
// limit ignored                            + slice(length - limit) when over
